# 项目初始化 —— 维护席执行

> **谁读这一份**：被「初始化项目」叫起来的那个会话，**它就是维护席**。
> **怎么触发**：新会话的第一句话**意思是「初始化项目」**就算——不管用哪种语言。
> 不要去匹配字面词，**按意思判断**：
> `初始化项目` / `Initialize the project` / `プロジェクトを初期化` / `프로젝트 초기화` /
> `Inicializar el proyecto` / `Initialiser le projet` / `Projekt initialisieren` /
> `Инициализировать проект` / `تهيئة المشروع` / `Inisialisasi proyek` …
> 意思对了就进这套流程，**不要反问「你是说 xx 吗」**。

**照顺序做，别跳。** 每一步都有收尾判据。
**判据是「不比第 0 步的基线差」，不是「全绿」**——只有第 5 步要求全绿。
（旧项目一上来就带着红的守门，要求中间每步全绿会当场死锁。）

---

## 第 0 步：先看清楚，一个字都别改

模板是**整个根目录覆盖**上去的，所以根目录里现在可能混着两拨东西。**这一步只看，不动。**

### 0.1 先读你自己的手册

`CLAUDE.md` 把你送到这一份，但**你这一席的手册是 `ai/roles/maintainer.md`**，先读它——
里面那条 ⛔ 说明了「改规范＝改几处」在**拷贝出来的项目里只算一处**，
不读它你会在第 5 步撞上一条你满足不了的规矩。

### 0.2 记一条守门基线（**这一步省了，后面会死锁**）

```
bash ops/verify/check-inbox.sh ; bash ops/verify/check-bugs.sh
bash ops/verify/check-paths.sh ; bash ops/verify/check-entrypoints.sh
bash ai/check-links.sh
```

**把这几条现在的结果抄下来。** 旧项目**多半一上来就有红的**——
比如旧文档里写死了一个测试机 IP，`check-paths.sh` 当场就红，
而能修它的是第 3、4 步。**所以中间几步的判据是「不比基线差」，只有第 5 步要求全绿。**
基线不记，你到第 5 步分不清那条红是你弄坏的还是它本来就红。

### 0.3 分清新旧

```
bash ops/verify/frame-scan.sh
```

- **B 类 = 0，且「清单里有、现在却没有」= 0** → **新项目**，走第 1、2、4、5 步。
- 否则 → **旧项目**，五步全走，**第 3 步是重头**。

**两件脚本不会替你做的**：

- **`archive/` `dist/` `tmp/` 没扫**（在活项目里它们本来就装杂物）。
  **初始化时手工看一眼**——旧项目完全可能把东西放在同名目录里，那样它对脚本是隐形的。
- **B 类为 0 不等于新项目。** 还要排除 C 类撞名（见 3.1）。**只有两者都干净才算新的。**

### 0.4 摸清 git 的底（**旧项目必做，而且要先做**）

覆盖发生在你被叫起来之前，**被盖掉的文件只能从 git 里捞**。先确认你捞的是**这个项目的** git：

```
git rev-parse --is-inside-work-tree     # false → 旧项目没进 git，被盖的东西真没了
git rev-parse --show-toplevel           # 必须等于项目根目录！
```

🔴 **`--show-toplevel` 指向上一层目录，说明你在别人的仓库里。**
这时候 `git show HEAD:README.md` 捞出来的是**另一个项目的文件**，
照着「恢复」等于拿陌生人的内容覆盖你的。**对不上就停，先问需求方。**

确认之后，这条命令是本指南里最值钱的一句：

```
git status --short          #  M 开头的 = 被模板盖掉的旧文件，这就是 C 类的名单
git ls-tree -r HEAD --name-only   # 旧项目原本有哪些文件（注意：旧 .gitignore 藏起来的不在里面）
```

**C 类不用靠眼力逐个猜**——`git status` 直接给你答案。旧项目没进 git 才需要人工比对，
那种情况**立刻如实告诉需求方：哪几个文件可能已经被盖掉且找不回来**。

## 第 1 步：一次问清两件事（**用弹窗选择题**，不要挤牙膏）

**两个问题一起用会话自带的选择控件弹给他**（`ai/rules/workflow.md` §四之二），
**不要把选项排在正文里等他打字**。每个都给选项和推荐值：

**Q1 · 项目叫什么？**
默认＝**仓库根目录的名字**（把它作为首选项摆出来）。需求方要换名字就用他给的。

**Q2 · 用哪种语言沟通？**
这个答案同时决定三件事：

1. **这个会话之后用这种语言跟需求方说话**；
2. **以后三席的会话也用这种语言**（写进 `CLAUDE.md` 顶部那行「沟通语言」）；
3. **文档内容翻译成这种语言**（见第 2 步）。

🔴 **他说话的语言已经和这份模板一致，就别摆三个选项了。** 那三个选项会塌成同一个答案，
而 `ai/rules/workflow.md` §四之二 明写「两个选项其实同一件事，是在浪费他一次注意力」。
这种情况**一句话确认就行**：「文档和沟通都用 English，对吧？」

语言不一致时才真的是选择题：**他的语言**（首选）／**保持文档现状、只用他的语言对话**（代价：
以后三席读的文档和他说的话不是一种语言，每次引用都要现译）／**English**。

> **Q1 天然只有一个真选项**（根目录名）＋ 一个自由输入。控件自带「其他」，
> **不用硬凑第二第三个**——`workflow.md` §四之二 的「只有一个合理做法就直接做」在这里也算数。
> 旧项目还有一条：**先做完 0.4**，因为被盖掉的 `README.md` 里往往写着产品真名，
> 那个名字和根目录名不一致时，得把两个都摆给他。

> **答完再动手。** 这两个答案会影响后面每一个文件，先改后问等于白改。

## 第 2 步：本地化 —— **只译内容，不译路径**

目标语言是 English 就跳过这一步。否则：

### 要译的

- 所有 `.md` 文档的**正文**：说明、表格里的文字、注释、给人看的例句。
- 脚本（`.sh` `.ps1`）里**给人看的部分**：注释、`echo` 出来的提示文案。

> **注意「目录名」和「内容产物的文件名」不是一回事**（`ai/rules/layout.md`）：
> **目录名一律英文**；而**技术方案、数据库设计、说明文档这类内容产物，文件名跟着沟通语言走**。
> 旧项目搬进来的文档，**原来叫什么就还叫什么**——**不许顺手规范化成英文缩写**，
> 那等于把需求方认得的名字换成只有你认得的代号。

### 不许译的

| 不许译 | 为什么 |
|---|---|
| **所有目录名与文件名** | 结构要跨语言通用；守门脚本、索引、跨项目复用全靠它们对得上 |
| **编号格式** `T-####` `AD####` | 机器和人都按它检索 |
| **守门输出标记**：`BUILD-OK` `TEMPLATE-SYNC-OK` `CHECK-PATHS-OK` `INBOX-OK` 等 | **脚本之间靠这些字符串对接**，译了就断 |
| 代码、变量名、JSON 的 key、配置项 | 同上 |

### 会咬人的那一类：**机器也在读的词**

有些词既写在文档里（给人看），**又被脚本 grep**（给机器看）——
状态词（`待实施` `开发中` `待审` `已过` `挂起` `作废`）、收件簿的 `待处理` 就是这种。
**译文档不改脚本 = 守门静默失效**，而且**没有任何报错**。

**规矩**：这类词**译的时候同轮改脚本**，清单在 **`ai/glossary.md`**，
哪个词被哪个脚本读、改了要同步改哪里，都写在那里。**先读它再开译。**

### 收尾判据（**不比第 0 步的基线差**，不是要求全绿）

```
bash ops/verify/check-inbox.sh      → INBOX-OK
bash ops/verify/check-bugs.sh       → BUGS-OK
bash ops/verify/check-entrypoints.sh → ENTRYPOINTS-OK
bash ops/verify/check-paths.sh      → CHECK-PATHS-OK
bash ai/check-links.sh              → 引用完整性 OK
```

**原本绿的现在红了，多半是你译穿了「机器也在读的词」**——回 `ai/glossary.md` 对一遍。
**本来就红的**（旧项目带进来的）**不用管**，那是第 3、4 步的活。

## 第 3 步（**旧项目专属**）：分清谁是谁，再迁移归档

### 3.1 先分三类，不要急着搬

拿 `ai/frame-manifest.txt` 逐项比，把根目录下每一样东西归进三类：

| 类 | 是什么 | 怎么处理 |
|---|---|---|
| **A · 我们的** | 清单里有，内容也是模板那份 | **不动** |
| **B · 旧项目的** | 清单里没有 | 按 3.3 归类迁移 |
| **C · 撞名的** | 清单里有**同名文件**，内容却是旧项目的（**真正会撞的几乎只有 `README.md`**——原因见下方两个误会） | **最危险的一类**，用 `git status` 找出来（见下），**先捞回原件再说** |

**C 类怎么找：别靠眼力，用 `git status`。** 0.4 里那条命令直接给你名单：

```
git status --short        #  M 开头的就是被模板盖掉的旧文件 —— 这就是 C 类
git show HEAD:<那个文件>   # 把原件原样捞回来
```

**捞回来的内容不要直接盖回去**——先原样存进 `archive/legacy-<日期>/`，再决定怎么合并
（旧 `README.md` 的那句介绍，往往正好是第 4 步要填的项目一句话）。

> **两个常见的误会先说清楚**：
> **`.gitignore` 不是 C 类**——模板发的是 `gitignore.template`，不叫 `.gitignore`，盖不到它，
> 它会出现在 B 类里，处理方式见第 4 步的「两个 `.gitignore` 怎么合」。
> **`docs/` `src/` 这种目录也不是 C 类**——清单是**文件级**的，同名目录只是并排放着，
> 真正撞上的只有**同名文件**。
>
> **旧项目没进 git**（`git rev-parse --is-inside-work-tree` 是 false）：原件是真没了。
> **立刻如实告诉需求方哪几个文件可能已经被盖掉**，别装作没事，也别自己编一份「大概是这样」的。

### 3.2 出映射表，**确认了再动**

出一份**迁移映射表**：**旧路径 → 新路径**，或者「不迁」+ 为什么。
**放 `claude-outputs/maintainer/<日期>-迁移映射表.md`，不要放 `tmp/`**——
`tmp/` 不入 git 且每段清空，而这张表是第 5 步维护记录要引用的证据。

**给需求方过一遍再动手。** 这一步省不得——搬错了再搬回来比一开始搬对贵十倍。

### 3.3 常见东西往哪归（按 `ai/rules/layout.md`）

| 旧项目里的 | 归到 |
|---|---|
| 源码 | `src/<project>/` |
| 给人看的文档、部署说明、排障 | `docs/` |
| 需求、原始聊天记录、验收标准 | `product/requirements/`（原话进 `verbatim/`） |
| 设计稿、原型、图标 | `product/design/` |
| 编译产物、安装包、镜像 | `dist/`（**不入 git**） |
| 打包/中转/一次性脚本与副本 | `tmp/`（**不入 git**） |
| 历史方案、老版本、说不清但不敢删的 | `archive/` |
| 已有的待办、任务单（**未完成的**） | 按 `ai/rules/workflow.md` §三 转成 `ai/tasks/T-####` |
| 已有的待办里**已完成的那些** | **不迁**，快照里留着就行。迁进队列只会让队列一开张就是脏的 |
| 已有的决策、结论、约定 | 转成 `ai/decisions/` 的条目 |
| **跑起来用的脚本**（dev/run/test 这类） | 跟着源码走：`src/<project>/` 里那门语言放脚本的地方。**部署运维的才进 `ops/scripts/`** |

**三条容易踩的**：

- **迁移来的需求不进收件簿。** 收件簿只收**需求方现场说的话**；
  把历史需求塞进去会让 `check-inbox.sh` 一开张就红，而第 5 步要求它绿。
  历史需求**原文进 `product/requirements/verbatim/`，要做的直接转成任务或规格**。
- **同一件事别迁成两条。** 旧 `TODO.md` 里的一条和旧需求文档里的一段常常是同一件事——
  合成一条任务，任务的「依据」指向那份 verbatim。
- **`feature/` 还是 `suite/`**：单个功能的定稿设计进 `feature/<名>/`，
  整套运行态镜像（桌面、安装器、手机端这种）进 `suite/<套>/`。说明在 `product/README.md`。

### 3.4 迁移的四条硬规矩

1. **是复制，不是移动。** 旧结构**整体快照**进 `archive/legacy-<日期>/`（**`<日期>` 用 `YYYY-MM-DD`**），
   **一个字不删**。需求方以后要核对，靠的就是这份快照。
   > `ai/rules/layout.md` 有一条「不要按段堆旧文件副本」——**这份快照是它唯一的例外**，
   > 理由是旧项目可能根本没进过 git，git 里找不回来。例外只此一次，迁完不再加第二份。
2. **覆盖率核对**：旧树**每一个文件**都要在映射表里有归宿，**unmapped 必须是 0**。
   「大概都搬完了」不算数——数出来：旧树清单用 `git ls-tree -r HEAD --name-only`
   加上 `frame-scan.sh` 的 B 类，**再加上你在 0.3 手工看过的 `archive/` `dist/` `tmp/`**
   （脚本不扫那三个，旧项目放在同名目录里的东西对它是隐形的）。
3. **内容核对**：整目录搬的用 **sha256 集合比**；逐份改写过的，**列出每一份为什么不一致**。
   **不许出现「没有对应物且说不清」的文件。**
4. **归档目录全量入 git**，**之后**再出一份「这里面什么可以删」的清单给需求方确认。
   **你不替他删。**

### 3.5 收尾判据

- 映射表 unmapped ＝ 0，需求方已确认。
- `archive/legacy-<日期>/` 已入 git。
- 「可以删什么」清单已交给需求方（**删不删是他的事**）。

剩下的（`ai/roles/*`、`ai/rules/{workflow,layout}.md`、各目录 README）**不用改就能用**。

> **第 8 条之后，`ai/frame-manifest.txt` 就不再和本仓库一一对应了——这是正常的。**
> 那份清单是**「模板长什么样」的快照**，用来在初始化那一刻分辨谁是谁，
> **不是本项目以后的校验表**。初始化做完它就功成身退了。

### 旧项目：两个 `.gitignore` 怎么合

旧项目自己带着一个 `.gitignore`，模板又要你建一个。**不要直接覆盖**：

1. 旧的那份**先进快照**（`archive/legacy-<日期>/.gitignore`）；
2. 逐条看旧规则：**已经被模板覆盖的就丢**（例：旧的 `*.pyc` 被模板的 `*.py[cod]` 包住了），
   **因为产物改放 `dist/` 而失效的也丢**（例：旧的 `/build`）；
3. **剩下的才并进新的那份**，并在旁边写一句它是从哪来的。

**还有一件**：审查席的 `ai/specs/{testing,architecture,database,tech-stack}.md` 都是空骨架，
**归它填，不用你代劳**。

## 第 5 步：收尾

1. **守门全绿**：`check-inbox` · `check-paths` · `check-bugs` · `check-entrypoints` · `ai/check-links.sh`。
   **这一步才要求全绿**（第 0 步记的基线到这里必须全部被消化掉）。
   还红着就说清楚是哪条、为什么、谁来修——**不许把红的说成「已知问题」放过去**。
2. **`.gitignore` 存在**（第 4 步第 1 条最容易被跳过，所以这里再验一次）：
   `ls -a .gitignore` 有，且 `git check-ignore -q dist tmp` 通过。
3. `ai/state/now.md` 写上：**项目已初始化、项目名、沟通语言、（旧项目的话）迁移摘要**，
   并把顶部 🔔 行的日期设成今天。
4. **维护记录第 1 条**（`ai/rules/maintenance-log.md`）：项目名、语言、旧项目迁移做了什么，
   **附需求方原话逐字摘录**，并指向 `claude-outputs/maintainer/<日期>-迁移映射表.md`。
   > 那份记录里有一条「`check-template-sync.sh` 红着不算维护完」——
   > **那条只对拥有模板的仓库算数**，你这个项目里根本没有那个脚本，**跳过它**
   > （`ai/roles/maintainer.md` 开头那条 ⛔ 说明了原因）。
5. **旧项目多一件**：把「归档目录里什么可以删」的清单交给需求方确认。**你不替他删。**
6. 告诉需求方**接下来怎么用**：开三个会话，各说一句 `你是开发者` / `你是审查者` / `你是监督者`；
   有事只跟审查席说；要测就说「审查并测试」；规矩改了对在跑的会话说「重载规范」。

## 附：四个角色是干什么的

| 角色 | 一句话 | 产出落哪 |
|---|---|---|
| **开发者** | 可靠地把功能实现出来（不是「实现出来」就行）；**交审前先自测** | `src/` · 任务文件的「开发者回报」「自测」 |
| **审查者** | 资深技术专家**兼专业测试**：审代码/审方案、测功能与 UI、对需求方收需求、排活 | 任务文件的「审查结论」「测试结论」· `ai/decisions/` · `ai/specs/` |
| **监督者** | 需求方的全能技术顾问，单独沟通，不占用开发主线 | `claude-outputs/supervisor/`（原样入库） |
| **维护者** | 维护这套模式本身：规则、角色手册、模板（中文版 + 英文版）、守门 | `ai/rules/maintenance-log.md` · `ai/template*/` |

**关键机制：开发者和审查者写同一个任务文件。** 中间插新任务不影响老的；任何一方掉线，
另一方从文件就能接上——**不需要把上下文塞在对话里，会话换了也不丢**。

## 这套结构解决的是什么问题

它是从一个真实项目里长出来的，那个项目踩过这些坑：

| 坑 | 这套结构怎么挡 |
|---|---|
| 文档涨到 1.7MB，每个会话开场吃掉几十万 token | 每个文件有**读它的理由和行数上限**（`ai/rules/layout.md` §三）；开场必读约 260 行 |
| 同一件事在四本待办里状态不一致 | **待办只有 `ai/tasks/index.md`，交接只有 `ai/state/now.md`**，不许开第二本 |
| 台账「实现」列全不可信，没人知道还剩什么 | 每段收尾**必须**改动过的每条决策的实现列（收尾四件之一） |
| 一件事的上下文散在三个大文件里 | **一个任务一个文件**，审查和开发写同一份 |
| 改了目录名，部署脚本里的老路径没人回头扫 | 路径只在 `ops/paths.ps1` 定义一次 + `ops/verify/check-paths.sh` 守门 |
| 换一台测试机要改一百多处 | 机器只在 `ops/machines.json` 定义 + 同一条守门扫写死 IP |
| 加了守门脚本，但守门自己是坏的没人发现 | **新加的守门必须当场造错跑一次，贴「它确实红了」的输出** |
| 「做完了」＝ 代码写完了，真机一跑全是坑 | 开发交审前**自测**；审查席是**专业测试**，需求方说「审查并测试」就全测一遍 |
| 临时文件越堆越多，最后要人工清 GB 级垃圾 | 不入库的只有 `tmp/` 和 `dist/`；`tmp/` 谁产生谁清、本段收尾删 |

**如果你的项目不需要某一条，就删掉它**——但删之前先想想上面那一列。每一条都是真事换来的。
