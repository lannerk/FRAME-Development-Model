# product/ —— 产品定义

| 路径 | 放什么 | 规矩 |
|---|---|---|
| `vision.md` | 产品愿景（十点架构）。**它是决策台账的上位依据** | 改它要需求方拍板 |
| `requirements/verbatim/` | **需求方原话，一字不改，只追加。** 文件名 `<日期>-<话题>.md` | 复述会丢东西——「多段切割上传」被复述成「只是传得可靠」，把它真正的目的丢了 |
| `requirements/specs/` | 审查者整理出的**可验收规格**（做什么 / 边界 / 验收点 / 不做什么） | 一个功能一个文件 |
| `requirements/formal/` | 正式需求文档 R-xx | 编号需求的唯一出处 |
| `design/prototype/_PROJECT_/suite/` | **整套原型**（= 运行态镜像：桌面、安装器、手机端…）。改前端要同轮镜像过来 | 改完跑原型自检 |
| `design/prototype/_PROJECT_/feature/<名>/` | **单个功能的定稿设计**：原型 html + 图标 + 说明。**开发从这里取，不从草稿区取** | 每个目录一份 README 写明开发怎么用 |
| `design/ui/` | **确认后的基线资产**：图标 SVG、配色、标注图 | 已确认的东西，**开发不要擅自改** |
| `design/reference/` | 参考设计、竞品截图 | 只当线索 |

**原话 → 规格 → 任务**，三步不要跳：
原话进来之后**审查者当轮把它转成规格或任务**，不要让它躺在 `verbatim/` 里等人翻。

**给需求方的问题一律是选择题**，不是开放题：两三个选项 + 各自代价 + 推荐哪个、为什么。
（反例：「VPN 一期做哪些协议？」→ 正例：「A: IKEv2+WireGuard（推荐，NM 原生支持，不引第三方）/
B: 加 OpenVPN（多一个包，有一部分配置指令 NM 不认，要在界面上标出来）/ C: 全上」）
