# 开发计划

> **谁写**：审查席。**谁拍板**：需求方。
> **什么时候要**：一个需求大到**一条任务装不下**——要分批、要排先后、要跨多个功能——就先出计划再开任务。
> 小改直接开任务，**不要为了走流程造计划**。

| 文件 | 是什么 |
|---|---|
| `roadmap.md` | **里程碑总表**：有哪几个里程碑、各自的目标与验收、现在到哪了 |
| `milestones/M-##-<名>.md` | 一个里程碑一份：范围、拆成哪几条任务、依赖、风险、什么算做完 |

## 三条规矩

1. **计划不是任务队列。** 计划说「分几批、为什么这个顺序」；具体干什么在 `ai/tasks/`。
   两边用编号互相指：里程碑文件列 `T-####`，任务文件写 `关联里程碑: M-##`。
2. **每个里程碑必须有可验收的「做完了」**——能用命令或截图证明的那种。
   写不出验收标准的里程碑，是愿望不是计划。
3. **计划会变，改的是原件。** 顺序调整、砍范围、加批次，**直接改那一份 + 加一行变更记录**，
   不许开 `roadmap-v2.md`。变更的原因写清楚（需求方拍的还是实测推翻的）。
