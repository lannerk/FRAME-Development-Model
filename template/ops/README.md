# ops/ —— 部署与运维

| 子目录 | 放什么 |
|---|---|
| `machines.json` | **测试机清单——全项目唯一的机器信息出处**（见下） |
| `paths.ps1` | **仓库内路径只在这里定义一次**，所有 `.ps1` 开头 dot-source 它（见 `docs/ops/realmachine.md` §四） |
| `scripts/` | 部署运维脚本的**真实实现** |
| `verify/` | 守门脚本：`check-paths.sh`（写死的 IP 与旧目录名）· `check-inbox.sh`（收件簿有没有漏）· `check-bugs.sh`（bug 闭环断没断）· `check-entrypoints.sh`（别名入口还是不是指针）· `frame-scan.sh`（初始化时分辨谁是谁）· `check-template-sync.sh`（模板跟没跟上） |
| `units/` | 服务单元（systemd 等） |

**常用脚本在仓库根留一个薄壳**（十来行，只转发到 `ops/scripts/` 里的实现），
这样需求方在仓库根就能直接跑，不用记深路径。
**薄壳不许长出逻辑**——它一旦有逻辑，就又是第二份真相了。

**这里不放**：源码跟着走的自检脚本（那些在 `src/<project>/tools/`，和被它扫的代码待在一起）；
二进制与升级包（在 `dist/`，不入库）。

## 一轮拍板完：**审查席提交本地 git，需求方负责推送**

**谁改完谁提交 —— 不是只有审查席**：

| 谁 | 什么时候提交 |
|---|---|
| **审查席** | 一轮审查结束、给完结论之后 |
| **维护席** | **改完规范之后**（规则、角色手册、`CLAUDE.md`、守门脚本、两份模板、维护记录）。标题写清改了哪条规矩 |
| 开发席 | **不提交**。它的改动由审查席那一轮一起提交——**自己写的自己提交，等于绕过了审查** |

**跑一次**：

```
bash ops/scripts/commit-round.sh "<一句话标题>" --seat <你这一席>   # 先看提交信息长什么样：加 --dry
#   --seat 维护席/审查席/开发席/监督席：只提交归你的那几份（归属表 ai/rules/layout.md §七）
#   横跨两席以上又没给 --seat：脚本停下并列出谁的是哪几个；确实要一起提交才加 --all-seats
```

它只做 **`add` + `commit`**，**永不 push**。推送是需求方的事。

### 🔴 这台机器上开着 SourceTree，所以有五条不许

| 不许 | 为什么 |
|---|---|
| **不许 push** | 推不推、推哪个远端，是需求方的决定 |
| **不许 amend / rebase / reset / cherry-pick / force** | 那些**改写历史**。SourceTree 正开着这个仓库，历史被改写它会显示成一团乱麻，要人工恢复 |
| **不许动 `git config`** | `core.autocrlf` 这类是需求方 Windows 侧的设置，动了满屏假 diff |
| **不许新建或切换分支** | 就在当前分支上提交；切了分支需求方在 SourceTree 里会找不到自己的改动 |
| **不许删 `.git/index.lock`** | 那把锁意味着**有 git 正在操作**（多半就是 SourceTree）。抢锁会让它当场报错。脚本遇到锁就原样退出 |

**守门红着不许提交。** 「红着就是没做完」——带红提交等于把「没做完」写进历史，
下一个人 clone 下来还会以为这是个干净基线。确实要带红提交（比如这一轮就是为了修它）：
`ANYWAY=1 bash ops/scripts/commit-round.sh "<标题>"`，**提交信息里会写明它是带红进去的**。

**提交人是谁**：这台机器没有 git 全局身份（需求方的身份在 Windows 侧 global 配置里，这边看不见）。
脚本**从上一条提交的作者取**，用 `-c` 临时传进去——**不写进 `.git/config`**（那会覆盖他的全局身份）。
提交信息末尾带一行 `Co-Authored-By: Claude`，**说清这条是 AI 生成的**。

脚本自己会先查四件，任何一件不过就**原样退出、什么都不动**：
`index.lock` 在 / 处在未完成的 merge·rebase·cherry-pick / HEAD 游离 / 没有可提交的改动。

> **`-c core.fileMode=false`**：脚本从挂载盘跑，Linux 侧看到的可执行位和 Windows 侧不一样。
> 不关掉就会把一堆 `mode change 100644 → 100755` 塞进提交——纯噪音，还会让 SourceTree 的 diff 满屏飘红。

### 提交信息里有什么

标题 + 日期 + 改动范围（`--shortstat`）+ **这一轮涉及的 `T-####` / `B-####` / `AD###`** + **守门一行汇总**，
末尾一句「未推送，请在 SourceTree 里确认后 push」。编号是从改动的文件名和 diff 里**捞出来的，不是人填的**——
人填会漏，捞出来的不会。

## 真机改完必须回到仓库：**写不回去也要挂账**

**仓库是唯一的源，真机是易变现网。** 只改真机不改仓库，下一段有人从仓库出发就会把它覆盖回去——
**而且两边都不报错**，这是最难查的一类。

- **开发席**：真机改完**同轮写回**，逐个 `sha256sum -c` 对账。**没对账 = 没写回。**
- 写回被拒（Windows 占用）：按 `docs/ops/realmachine.md` 的四级办法试，**不要反复重试同一招**。
- **四级都不行 → 挂账**：把那几份放 `tmp/writeback-pending/`（保持原有的相对路径），
  并在回报里写清**哪个文件、为什么没写进去、要怎么合**。
- **守门**：`bash ops/verify/check-writeback.sh` —— 那个目录非空就是红。
  **挂着不算交付完成**，审查席看到红的**不许判过**。
- **审查席不替他合功能代码**（自己写的自己审等于没审）。它能做的是：
  在结论里点名这条、必要时让需求方在 Windows 侧关掉占用的程序，**然后打回让开发自己合**。

## `规范巡检`：需求方觉得跑偏了的时候

需求方说一句 **`规范巡检`**，维护席跑一条命令，**只回一张表**：

```
bash ops/verify/check-all.sh          # 全绿就一行；有红的再 -v 看详情
```

**先跑脚本再读文件。** 能机器判的（断链、写死的 IP、收件簿、bug 闭环、台账字段与状态双写、
行数预算、入口文件、回写挂账、模板同步）一次跑完，**只有红的才值得人去看**——
把八个脚本的输出一条条读进上下文是纯烧 token。

机器判不了的（规矩本身合不合理、有没有自相矛盾、该不该加一条）才轮到人读，
而且**先读维护记录**看上次改到哪，别从头翻。
