# src/ —— 源码（多项目）

```
src/
├── <项目子目录>/      主项目
│   ├── <代码目录>/
│   ├── tools/         跟着源码走的自检脚本（扫的就是这里的代码）
│   └── <项目元信息：go.mod / package.json / README.md / VERSION …>
└── <第二个项目>/      将来要加的，**同级新建，不要塞进第一个里面**
```

**为什么多一层项目目录**：一个仓库常常会长出第二个项目（服务端、CLI、SDK）。
一个项目一个目录、各自带自己的依赖清单和 `tools/`，互不干扰；
公共的东西（部署脚本、服务单元、机器清单）在 `ops/`，**不在任何一个项目里面**。

---

## 源码目录规范：什么能放在项目根下

**项目根目录下只允许这些**，别的一律有自己的家：

| 允许 | 说明 |
|---|---|
| 代码目录 | 按语言/框架的惯例 |
| `tools/` | 跟着源码走的自检脚本 |
| 依赖与元信息文件 | `go.mod` / `package.json` / `VERSION` / `README.md` … |

**下面这几类，不许出现在源码目录里**（括号里是它该去的地方）：

| 不许放 | 该去哪 | 为什么 |
|---|---|---|
| 部署 / 运维脚本 | `ops/scripts/`、`ops/units/` | 它们部署的是产物，不是源码的一部分；放在源码里会跟着源码打包 |
| 编译产物、安装包、`*.tgz` | `dist/`（不入库） | 随时能重新生成 |
| 搬文件用的一次性包、临时脚本 | `tmp/`（不入库） | 用完自己删 |
| 设计稿、预览页、效果图 | `product/design/` | 那是设计资产 |
| 运行环境的状态快照 | `claude-outputs/shared/measurement/` | 那是证据，不是源码 |
| 截图、实测输出 | `claude-outputs/shared/` | 同上 |

### 源码目录长出不认识的文件时，查三件

1. **谁引用它？**（`grep -rl` 全仓库）
2. **版本控制跟不跟踪它？**
3. **它的内容是不是别处已经有了？**（同名文件、只差换行符的副本、上游能重新生成的产物）

三个答案就能定它**该搬去哪、还是不搬**。
实践里最常见的三种：**一次性搬运包**（零引用、不跟踪 → 不搬）、
**同内容的第二份副本**（只差换行符或路径 → 留一份）、
**运行环境快照**（看着像源码，其实是证据 → 进 `claude-outputs/`）。

## `src/<project>/` 里面归语言管，不归这套模板管

**按那门语言/框架自己的官方约定组织目录**——Go 就 `cmd/` `internal/` `pkg/`，
Maven 就 `src/main/java`，Python 就包目录 + `pyproject.toml`，前端框架就按脚手架生成的那套。

**不要把别的语言的习惯套上来，也不要为了「看起来整齐」自己发明一套。**
违背语言约定的代价是**它自带的工具链全部失灵**（构建、测试发现、打包、IDE 索引），
而且每个新来的人都要先学你这一套。

本项目用的是哪套约定，写在 `ai/specs/tech-stack.md`，`docs/repo-layout.md` 提一句指过去。
