# 本项目的测试方法

> **为什么要有这一份**：`reviewer.md` §六 那八类说的是「**要测什么**」，那是通用的；
> 「**怎么测**」每个项目都不一样——有的要连测试机远程操作、要挂调试器进某个引擎，
> 有的在浏览器里点两下就够了。**手段在这里定一次，以后照着测、跟着改。**
>
> **审查席开测之前先把这份填了。** 填不动的类别也要留行，写清缺什么才能测——
> **空着等于没想过**，而没想过的那一类就是将来漏掉的那一类。

## 怎么填

每一类写清四件，缺一件这一类就不算定好：

| 要写的 | 说明 |
|---|---|
| **手段** | 用什么去测（浏览器点、远程连测试机操作、发请求、挂调试器、跑脚本……） |
| **环境** | 在哪台机器上测。**机器按 `ops/machines.json` 的 `id` 引，不许写死 IP**；连法见 `docs/ops/realmachine.md` |
| **动作** | 跑哪条命令 / 点哪条路径 / 发什么请求。**要能让别人照着重跑** |
| **证据** | 测过之后留下什么：命令输出 / 请求与响应 / 截图 / 数字。放 `claude-outputs/reviewer/<日期>-测试/` |

## §0 要测什么：通用八类（从 `ai/roles/reviewer.md` §六搬来）

| # | 测什么 | 怎么算测过 |
|---|---|---|
| 1 | **功能测试** | 对着任务的「验收」逐条走，每条标 通过／不通过；不通过的给**最小复现步骤** |
| 2 | **UI 验收** | 对着定稿原型与 UI 规范逐项比：布局、字号、间距、颜色令牌、**空态／加载态／错误态／禁用态**、窄屏、深色。**截图为证** |
| 3 | **接口测试** | **真发请求**：正常 + 缺参 + 超长 + 越权 + 重复提交。记下 方法／路径／状态码／响应体片段 |
| 4 | **端到端操作测试（E2E）** | 就是**照着用户那样一路点下去**。必点：中途返回、刷新、连点两下、断网重连、换个账号再来一遍 |
| 5 | **性能测试** | **要有数才算**：冷启动、首屏、接口 p50/p95、内存与 CPU、跑久了会不会涨。写清在哪台机器上测的 |
| 6 | **用例覆盖** | **有用例库才做**；没有就写「本项目暂无用例库」跳过，不必硬造 |
| 7 | **回归测试** | 这次改动碰过的公共依赖，**谁在用它就重跑谁**；**修过的 bug 必须重跑一次**——它最会复活 |
| 8 | **全量测试** | 需求方说「全量」，或**发版／出包之前**：用例库整套 + 全部关键流程走一遍 |

### 测试的硬规矩

- **测试也是结论，同样要带依据。** 命令与输出 / 请求与响应 / 截图 / 数字，**四者取一**。
  「我测了，没问题」不算测过。
- **先写清这次测什么、不测什么**，不测的写明为什么（环境不具备 / 不在本轮改动范围）。
  **含糊的「全测了」比诚实的「这四项没测」危险得多。**
- **在真环境测。** 测不了就说测不了，别把「应该可以」写成「已验证」。
- **测出来的问题当场落地**：进收件簿 / 开任务 / 记一条决策。**只在对话里说过等于没说。**
- **不改功能代码这条不变。** 测出 bug 就开任务给开发，**不自己修**——自己修的人测不出自己的盲区。
- 测试结论写进**同一个任务文件**，在「审查结论」旁边加一节「测试结论」。
- 结论只有三种：`过` / `过（带遗留）` / `打回`。**「带遗留」必须有 `T-####` 兜着**，否则就是打回。

> **开发也会自测**（`developer.md` §五），但那是**他自己做的功能他自己看**。
> 你测的价值来自**你没写过这段代码**——所以别只复跑他跑过的那几条，**专挑他不会想到的边角**。

**两条附带的规矩**：

1. **每条都要写「最近一次真跑的日期」**——否则三个月后没人知道它还成不成立。

2. **取证在前，重启在后。** 服务一重启，栈就没了；**第一现场只有一次**。
