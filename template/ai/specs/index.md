# 技术方案索引

> **方案是「定了之后开工必读」的东西，不是参考资料。** 任务里写了 `关联方案:`，开工前就要读那一份。
> 方案**随实现更新**：实现和方案不一致时**改方案**，不要让它停在提案那天。
> 文件名不带「技术方案-」这类前缀（目录已经说明了它是什么）。

## 转正与更新（和设计稿同一套规矩）

**草稿阶段**在 `claude-outputs/reviewer/` 里写，怎么改都行。
**审查者与需求方确认之后**搬到这里，并且：

1. 补文件头（状态 / 版本 / 最后更新 / 关联决策 / 引用它的任务 / 关联原型）；
2. **在下面的表里登记一行**（含「最后更新」）；
3. 任务文件里填 `关联方案:` 指向它。

**搬之前先定一件事：这是新方案，还是更新已有方案？**
**由审查者和需求方确认，不许自己定。** 判据是「**它管的是不是同一块功能**」，
**不是「这次改动大不大」**——一个功能加个新选项、换套实现，管的还是那个功能，那就是**更新原来那一份**。

| 情况 | 怎么做 |
|---|---|
| **新的一块功能** | 新开 `<名>.md`，补文件头，在表里加一行 |
| **已有方案的新版** | **直接改那一份**：bump 版本 + 加一行变更记录 + 更新表里的「最后更新」 + 到引用它的未结任务里各留一行提醒 |

🔴 **不许开 `xxx-v2.md` `xxx-新.md` 这种文件。** 同一块功能散成两份，开发就不知道该信哪个——
而这种错没有任何症状，直到有人照着旧的那份做完了才发现。作废的才移进 `archive/` 并在下面划掉。

**四条规矩**：①任务的「关联方案」必须指向一份方案或一条 AD；②谁改实现谁改方案，同一段里做完；
③「引用它的任务」是双向的；④方案不记「实现到哪了」——那是任务和决策实现列的事。
