# FRAME —— AI 四权分立开发模式

> **Four-Role · Audited · Maintained · Evidence-based**
>
> 一套**目录结构 + 四份角色手册 + 一组守门脚本**。不是框架，不用安装，没有依赖。
> 拷进仓库、开几个 AI 会话、各说一个词，它就开始运转。

> 🧭 **拿这份模板开项目的人**：初始化时这份 `README.md` 会被换成**你项目自己的介绍**
> （`docs/guide/project-init.md` 第 4 步）。方法本身的完整说明在根目录 **`FRAME-Development-Model.md`**，
> 建议在你的新 README 里留一行指过去。

---

## 一、这是什么

让 AI 写代码，最贵的从来不是「让它写出来」，而是**让它可靠地写出来，并且一个月后还接得上**。

FRAME 的做法是：**把协作状态从对话里搬到文件里，再把「写的人」和「判的人」分成不同的会话**。

```
你（需求方）
   │  只跟一个人说话
   ▼
审查席 ──开任务──▶ 开发席 ──回报──▶ 审查席判过不过 ──▶ 提交本地 git
   ▲                                    │
   │  按需咨询                           └─▶ 决策台账 / bug 台账 / 现状
监督席（独立顾问）              维护席（只管规矩，不碰活）
```

四个会话，**互相之间不直接说话**，全部通过仓库里的文件交接。会话随时可以关掉重开——
**上下文不在对话里，在文件里**。

## 二、它解决什么问题

这些不是设想出来的，是一个真实项目一路踩出来的：

| 症状 | 为什么会这样 | FRAME 怎么挡 |
|---|---|---|
| 每次开新会话都要重讲一遍背景，越聊越贵 | 上下文只活在对话里 | **开场固定读几份文件**（有行数预算，守门盯着），其余按需 |
| 文档涨到上兆，开场就烧掉几十万 token | 没人规定哪份文件该多大 | 每份文件有**读它的理由和行数上限**；`check-budget.sh` 判**实际行数** |
| 同一件事在四本待办里状态不一致 | 谁都能开一本新的 | **待办只有一本，交接只有一份**；`check-ledger.sh` 判**双写一不一致** |
| 台账写着「待开发」，其实早就交付了 | 收尾没人回填 | 收尾必做清单 + 守门 |
| AI 说「已修复」，真机一跑还是坏的 | 「我觉得没问题」被当成结论 | **一切结论带依据**：源码行号 / 实测数字 / 官方文档，三者取一 |
| 加了自检脚本，脚本本身是坏的没人发现 | 没人验过守门会不会红 | **反向断言**：新守门必须当场造错跑一次，把「它确实红了」贴进回报 |
| 同一个 AI 写完自己说「没问题」 | 写的人和判的人是同一个 | **写的人和判的人是两个会话**，判的那个没有写代码时的假设 |
| bug 转述一遍就走样，开发修了另一个问题 | 只传了现象，没传还原条件 | bug 必须写全**环境 / 前置条件 / 步骤 / 现象**，缺一条不许转给开发 |
| 规矩用着用着就和实际做法两张皮 | 大家都在用规矩，没人在养规矩 | **第四席专门养规矩**，改一条要记账、要同步模板、要开新会话验三席真照做 |

> 最后一条是 FRAME 和常见「AI 协作约定」最大的不同：**它给规矩本身派了一个人**。
> 没有这一席，任何一套约定都会在三个月内退化成没人遵守的文档。

## 三、四个席位

| 席位 | 权 | 干什么 | 制衡它的是 |
|---|---|---|---|
| **开发席** | 执行权 | 可靠地把功能实现出来；**交审前先自测** | 审查席可以打回；但它能带依据反驳 |
| **审查席** | 审查权 | 定标准、判过不过、排活、对需求方收需求；**兼专业测试与架构设计** | 需求方可否决；开发席可带依据推翻；**争议可按需请监督席看一眼** |
| **监督席** | 监督权 | 独立盘查，直接对需求方负责，不占用开发主线 | 意见须经审查席核实才能进队列 |
| **维护席** | 规制权 | 维护这套模式本身：规则、手册、模板、守门 | 需求方确认才动；**不参与开发，不碰需求** |
| 你（需求方） | 拍板权 | 定方向、拍取舍 | —— 它是权力来源 |

**效力顺序**：

```
需求方拍板  >  审查席验证过的事实  >  监督席的意见  >  任何人的「我觉得」
规矩本身怎么定  →  维护席（需求方确认后）
```

**一条硬规矩**：规则、角色手册、`CLAUDE.md`、守门脚本**只有维护席能改**。
其余三席发现该加一条，**发一封信到 `ai/mail/to-maintainer/from-<自己>.md`**（信箱传话，台账传活），
**不必麻烦需求方当传输层**。（唯一例外：`docs/` 工程文档——被它挡住的人当场改。）

### 编外座位：研究席（R&D 线）

🔴 **四权结构不变——研究席有座位，没有一种权**：它的产出在被监督席核实之前，效力等同「我觉得」，
落在上面那条效力顺序的**最末端**。它不参与制衡结构，制衡它的是**需求方**和**可证伪的实验**。

它在一条**与开发线并行的 R&D 线**上工作，把「一个还没有名字的想法」带到「可以开工的项目」：
目录 `ai/RandD/`，口令 `研究者`，手册 `ai/roles/researcher.md`，守门 `check-randd.sh`，
终点是**毕业**（九条判据全绿 → 监督席核实 → 需求方拍板 → 监督席执行迁移）。
**要不要开这条线由需求方定，开发线不受影响**；不开就让 `ai/RandD/` 空着。

## 四、快速开始

**1. 拷出来**

```bash
# 中文项目
cp -r ai/template/.    ../my-project/
# 其他语言
cp -r ai/template-en/. ../my-project/
cd ../my-project && mv gitignore.template .gitignore && rm SYNC.md
```

**2. 开一个会话，第一句话说「初始化项目」**（用你习惯的语言说，**按意思识别，不匹配字面词**）

那个会话会认出自己是**维护席**，照 `docs/guide/project-init.md` 走：
用选择题问你**项目名**和**沟通语言** → 把文档本地化 → 带你填完几个空 → 跑守门收尾。

> **旧项目也走这一条**：把模板覆盖到旧仓库根目录，它会用 `ai/frame-manifest.txt`
> 把根目录分成「我们的 / 旧项目的 / 撞名的」三类，出一份迁移映射表给你确认，再迁移归档。
> **不会替你删任何东西。**

**3. 开会话，各说一个词**

```
开发者        reviewer / 审查者        监督者        维护者
```

什么都不说 = 开发者。**你只跟审查席说话**，其余三席由它协调。

## 五、一个完整的例子

你在用的时候看到一个 bug，从你开口到提交，全程是这样的：

**① 你 → 审查席**（你只跟它说话）

> 「点进设置面板再返回，列表空了」

**② 审查席**：记进收件簿（一句一行）→ **自己先复现一次** → 复现了 → 开 `ai/bugs/B-0007-<一句话>.md`：

```markdown
---
id: B-0007
severity: S2
source: 需求方
status: 已复现
---
## 复现（四件缺一条不许转给开发）
- **环境**：机器 `vm-dev` / v0.9.3 / main@a1b2c3d
- **前置条件**：已登录的普通账号，列表里至少有 3 条数据
- **步骤**：1. 打开列表 2. 点右上角设置 3. 点浏览器返回
- **现象**：期望列表还在，实际整列表空白；控制台 `TypeError: items is undefined`
- **复现率**：3/3
```

然后开一条任务 `T-0042`，里面填 `关联bug: B-0007`。

> **复现不了怎么办**：标 `待复现`，**回来问你要条件**（哪台机器、什么账号、第几步）。
> **不许把没复现的 bug 丢给开发去猜**——他会修成另一个问题。

**③ 你 → 开发席**：`审查完毕请继续`

开发席自己去队列拿优先级最高的那条，读 `T-0042`，**读 `B-0007` 拿到还原条件**，改完：

- **自测**：按任务的「验收」逐条走；有界面的**对着定稿原型一比一比**（四态 + 窄屏 + 深色，截图）
- 回报里写 **`修了哪些 bug: B-0007`**，把 bug 推到 `修复待复测`——**不许自己标已关闭**
- 状态推 `待审`

**④ 你 → 审查席**：`审查`（要全面测就说 `审查并测试`）

审查席核依据、跑守门。**因为回报里「修了哪些 bug」不是空的，它本轮必须复测**——
按 `B-0007` 的原步骤重跑，**这一步不挂在口令上**。过了才把 bug 推 `已关闭`。

**⑤ 审查席收尾**：

```bash
bash ops/verify/check-all.sh                    # 九条守门一次跑完
bash ops/scripts/commit-round.sh "修复设置返回后列表清空"
```

提交信息里的 `T-0042` / `B-0007` / 决策编号是**从改动文件和 diff 里捞出来的**，不是人填的。
**脚本只做 add + commit，永不 push**——推送是你的事。

## 六、日常口令

| 你说 | 对谁 | 意思 |
|---|---|---|
| `开发者` / `审查者` / `监督者` / `维护者` | 新会话 | 认领席位。什么都不说 = 开发者 |
| `研究者` | 新会话 | 认领**编外座位**研究席（R&D 线，见 §三）。这条线不开就用不到 |
| `初始化项目`（**任何语言**） | 新会话 | 该会话即维护席，走初始化流程 |
| `审查完毕请继续` | 开发席 | 去队列拿优先级最高的那条，接着做 |
| `审查` | 审查席 | 只审：核依据、读码、跑守门 |
| `审查并测试` | 审查席 | 审查照做，**再把八类能测的都测一遍** |
| `这条我要咨询监督` | 审查席 | 把这条结论开成**顾问任务**派给监督席 |
| `看任务` | 监督席 | 读派给它的那一条顾问任务（**它读队列的唯一例外**） |
| `监督已给出意见` | 审查席 | 读监督席的产出，结合它再给结论 |
| `重载规范` | 任何一席 | 规矩改了，**真的再读一遍**并说出变了什么 |
| `查信` | 任何一席 | 读 `ai/mail/to-<你这一席>/`：**一次过全读、去重、逐封处置**，处置完移进自己的归档 |
| `规范巡检` | 任何一席 | 跑 `check-all.sh`，只回一张表；**红了归谁按文件归属判**，只有维护席能据此改规矩 |

## 七、目录里有什么

| 目录 | 是什么 |
|---|---|
| `CLAUDE.md` | **AI 自动加载的入口**：身份口令、常用口令、铁律一句话版。**故意压得很短**（它每个会话都加载一次） |
| `AGENTS.md` | 别的 AI 平台的入口，**只写一句指路**指向 `CLAUDE.md`（两份入口会无症状分叉） |
| `ai/roles/` | 四份角色手册，**读完就能开工** |
| `ai/rules/` | 铁律 · 协作流程 · 目录规范 · 工程约定 · **维护记录** |
| `ai/tasks/` · `ai/bugs/` | 一任务一文件 / 一 bug 一文件 + 各自的索引 |
| `ai/decisions/` | 决策台账（编号 + 依据 + 实现到哪了） |
| `ai/specs/` | 定稿技术方案：架构 · 数据库 · 技术选型 · **怎么测** |
| `ai/state/now.md` | **现状与交接**：现在做到哪、别再踩什么 |
| `product/` | 需求（原话 / 规格）· 设计与原型 · **开发计划与里程碑** |
| `docs/` · `src/` · `ops/` · `dist/` · `tmp/` · `archive/` | 工程文档 / 源码 / 运维与守门 / 产物 / 临时 / 历史 |
| `ai/mail/` | **席间信箱**：`to-<收信席>/from-<发信席>.md` 只放未读 + 一席一份的归档。**信传话，台账传活** |
| `ai/RandD/` | **R&D 线的工作区**（编外座位研究席，见 §三）：一话题一个编号目录，**未拍板的一切**；不开这条线就空着 |
| `claude-outputs/` | AI 草稿区：截图、实测数据、报告、监督产出 |

**`src/<项目>/` 内部按那门语言自己的官方约定组织**——Go 就 `cmd/` `internal/`，
Maven 就 `src/main/java`，前端就按脚手架生成的那套。**这套模板不管 `src/` 里面。**

## 八、守门脚本

规矩不靠自觉，靠能跑出红灯的脚本。`bash ops/verify/check-all.sh` 一次跑完：

| 脚本 | 判什么 |
|---|---|
| `ai/check-links.sh` | 文档里指不到东西的路径 |
| `check-paths.sh` | 写死的机器 IP 与废弃的旧目录名 |
| `check-inbox.sh` | 你说过的话有没有还没处置的 |
| `check-bugs.sh` | bug 闭环断没断：**复现步骤下面有没有编号行**、修完有没有复测、关闭有没有依据 |
| `check-ledger.sh` | 任务字段齐不齐、**状态双写一不一致**、索引与实体对不对得上 |
| `check-budget.sh` | 行数预算与**开场必读总量**（判实际行数，不采信文档里写的数字） |
| `check-entrypoints.sh` | `AGENTS.md` 这类别名入口还是不是一句指路 |
| `check-writeback.sh` | 有没有改完没写回仓库、挂在一边的文件 |
| `check-template-sync.sh` | 模板跟没跟上（**比内容指纹，不比 mtime**——mtime 过不了 `git clone`） |
| `check-root.sh` | 仓库根上每一项都在清单里，旧目录名没复活，草稿区命名带日期 |
| `check-filenames.sh` | 有没有 Windows 上建不出来的文件名（跨平台协作会当场炸） |
| `check-mail.sh` | 信箱没烂掉：只放未读 · 没有陈信 · 没拿信箱派活 · 归档一席一月一份 |
| `check-randd.sh` | R&D 线的结构与索引（**没开这条线就自己跳过**）：归档目录各有 `INDEX.md` · 活文件没超行 · **九条判据全绿才许标「已毕业」** |
| 项目专属的几条 | 例如前端缓存串、源与镜像、CSS 类名撞车——**不适用的项目它们自己 SKIP** |

**一条设计原则贯穿它们**：

> **判「要保的那件事」本身，不要判它的文本影子。**
> 同一件事的文本形状有无数种写法，你堵得完的只是你想得到的那几种。
> 能执行就执行一遍看结果，不能执行再退回文本匹配，并写明「它拦不住哪几种形态」。

**新加的守门必须当场故意造错跑一次**，把「它确实红了」的输出贴进回报——
做不到反向断言的守门，给的是虚假的安全感，**比没有更危险**。

## 九、代价，说清楚

这套东西不是白拿的：

| 代价 | 具体是什么 |
|---|---|
| **要开好几个会话** | 一个人同时开四个窗口，比只开一个麻烦 |
| **所有事都要先经审查席** | 你想直接对开发说一句「把这个改了」，得先说给审查席。**换来的是不丢事** |
| **写文件有固定开销** | 每轮要更新现状、改状态、记决策。**换来的是换会话不丢上下文** |
| **小项目会觉得重** | 一个周末写完的小工具，用这套是杀鸡用牛刀 |
| **规矩要有人养** | 第四席不是摆设；没人养，三个月后文档和做法就是两张皮 |

**什么时候别用**：一次性脚本、几十行的小工具、你自己一个人两小时能写完的东西。
**什么时候值得**：项目要活过三个月、代码超过几千行、要交给别人接手、
或者**你已经被「AI 说改好了其实没有」坑过**。

## 十、常见问题

**能配别的 AI 平台吗？**
能。真入口只有 `CLAUDE.md`，其余平台各加一个它会自动加载的文件（`AGENTS.md`、`GEMINI.md`、
`.github/copilot-instructions.md` …），**内容只写一句指向 `CLAUDE.md`**。
**不要复制内容**——两份入口会分叉，而且没有任何症状。`check-entrypoints.sh` 盯着这件事。
真正的门槛不是入口文件，是那个平台的 agent 得有**读文件、写文件、跑命令**三样能力。

**换一种语言怎么办？**
`ai/template-en/` 是同一套东西的英文版，**路径一字不差，只有内容语言不同**。
初始化时会问你沟通语言，然后把文档译过去。
**注意有些词机器也在读**（状态词、守门标记），译了要同轮改脚本——清单在 `ai/glossary.md`。

**目录名要跟着翻译吗？**
不要。**目录名与结构性文件名一律英文**；
**技术方案、数据库设计、说明文档这类内容产物，文件名和内容才跟沟通语言走**。
搬文件、转正、归档的时候**原来叫什么就还叫什么**，不许顺手规范化成英文缩写。

**AI 自动提交 git 会不会把我的图形客户端搞坏？**
不会。`commit-round.sh` **只做 add + commit**，永不 push、永不 amend / rebase / reset / force、
不动 `git config`、不切分支、**不删 `.git/index.lock`**。
遇到锁或未完成的 merge 就**原样退出、什么都不动**。

**规矩改了，正在跑的会话怎么同步？**
对它说一句 `重载规范`。它得**真的再读一遍文件**并说出**这次变了什么**——
只回「好的」就是没读。新开的会话不用管，开场就会读到最新的。

## 十一、这份模板怎么演进

模板由**维护席**维护。改一条规矩 = 改三处：**你的项目 + 中文模板 + 英文模板**，
同轮完成，`check-template-sync.sh` 比内容指纹盯着。什么该进模板只有一条判据：

> **换一个项目，这条还成立吗？**
> 成立的（做事的方法、分工、目录职责、通用的坑）进；
> 不成立的（产品是什么、机器与路径、编号、某次事故的细节）不进。同步时**留道理、换例子**。

每一次改动连同**需求方的原话**记在 `ai/rules/maintenance-log.md` 里——
三个月后想知道「这条规矩为什么存在」，答案在那儿。

## 十二、从 GitHub 拿这套的人：怎么跟上源仓库的更新

你手上这套是**从源仓库的 `ai/template/` 复制出来的**，源仓库以后还会改规矩，
而**你没有它的提交权**——所以同步只有一个方向：**源 → 你的项目**。
你复制过来的那份里**已经带着 `ops/frame/frame-sync.sh`**，不用另外装什么。三步装好：

```
# ① 把源克隆到你项目的**同级目录**
cd <你的项目的上一层> && git clone https://github.com/<源仓库>/FRAME-Development-Model.git
# ② 你项目的 ai/frame-repo.conf 写三行：
#    role=consumer  /  home=../FRAME-Development-Model  /  push=no
# ③ 立第一份基线（记「你自己现在这样」，所以以后源那边的变化都算「源改的」→ 拉回来）
bash ops/frame/frame-sync.sh --adopt-mine
```

以后每次跟进：

```
cd ../FRAME-Development-Model && git pull && cd -   # pull 在源那边跑，它和你的项目是两个仓库
bash ops/frame/frame-sync.sh --sync                # 只报不改
bash ops/frame/frame-sync.sh --sync --apply        # 看懂了再写
bash ops/verify/check-all.sh                       # 规矩变了，守门也跟着变了
```

两条别忘：

- 🔴 `push=no` 一定要写。不写它，同步会试着把你的改动写回源仓库——你推不上去，
  只会把那边的工作区搞脏，而你以为同步成功了。
- 🔴 **自己的补充写成新文件**（`ai/rules/ours-xxx.md`），别改 FRAME 自带的那几份：
  新文件机制认得出是你的、永远不管它；改了自带的那几份，每轮都要处理一次 🔶。

**好几个项目怎么办**：源仓库**克隆一份就够**，每个项目各填一份 `ai/frame-repo.conf`
（都指向那一份克隆）、各立一份基线，以后一个项目跑一次同步。

细节在 `docs/guide/frame-sync.md` §五：首次没基线怎么走 · 分叉的三条路 ·
英文模板起的项目每条命令要加 `FRAME_TEMPLATE=ai/template-en` · 怎么判断自己跟上了 ·
为什么源仓库那边 `push=yes`、你这边 `push=no` 却不用任何开关（那份 conf **同步永不碰**）。
