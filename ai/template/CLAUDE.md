# <项目名> — AI 自动加载入口

> **项目名 = 仓库根目录的名字。** 第一次开工时，AI 按根目录名认项目，并把这一段换成一句话介绍
> （做什么的、技术栈是什么、有没有指定要用的核心框架/平台）。详细介绍写在 `README.md`。

> **沟通语言：`<初始化时填>`**（四席都用它跟需求方说话；目录名、文件名、编号、守门标记**一律英文**）。

> 这个文件**只负责把你送到该读的地方**。它每个会话都加载一次，所以一行都不多写。

## 二、常用口令

| 他说 | 意思 |
|---|---|
| `审查完毕请继续` | 对开发者：去 `ai/tasks/index.md` 拿状态＝`待实施` 的最高优先级那条，接着做 |
| `审查` | 对审查者：开一轮审查，去 `ai/tasks/index.md` 看状态＝`待审` 的那几条。**只审，不铺开测** |
| `审查并测试` | 审查照做，**外加把能测的都测一遍**：功能、UI 验收、接口、端到端操作、性能、用例覆盖、回归、全量（`ai/roles/reviewer.md` §六；本项目用什么手段测见 `ai/specs/testing.md`） |
| `审查完毕，可以让开发继续` | 审查者一轮结束时说的话，不是给你的指令 |
| `初始化项目`（**任何语言、意思对就算**） | 这个会话就是**维护者**，照 `docs/guide/project-init.md` 走：先用选择题问项目名与沟通语言，再本地化、（旧项目还要）分辨与迁移、填空、收尾 |
| `这条我要咨询监督` | 对审查席：把这条方案/结论开成一条**顾问任务**派给监督席（`workflow.md` §五之二） |
| `看任务` | 对监督席：去读**派给它的那一条**顾问任务（这是它读队列的唯一例外），给意见 |
| `监督已给出意见` | 对审查席：去读监督席的产出，**结合它再给结论**，然后关掉那条顾问任务 |
| `查信` / `有新信` | 对**任何一席**：读 `ai/mail/to-<你这一席>/`（三份，一个发信人一份）——**一次过全读、自己去重、同一件事只做一次**，然后逐封处置（照做／转成任务／拒收并回一封答复），处置完把那行移进 `ai/mail/archive/<你这一席>-<年月>.md`（**归档归收信人**）。**必须在会话里报一张小结：收到几封 → 去重后几件 → 每件怎么处置**（样子见 `ai/mail/README.md`）|
| `规范巡检` | 对**任何一席**：跑 `bash ops/verify/check-all.sh`，**只回一张表**；有红的再 `-v` 看详情。机器判不了的才人读。**红了归谁按文件归属判**；只有维护席能据此改规矩 |
| `重载规范` | 对**任何一席**：规矩改了，**当场把下面五份重新读一遍**，然后报告变化。见下方「※ 重载规范」 |

### ※ `重载规范` 具体做什么

**没有「自动重载」这回事。** 你开场读到的是**那一刻的副本**；文件后来改了，
你脑子里的还是旧的，**而且你不会有任何感觉**。所以这个口令要求**真的再读一遍**（用工具读，不是回忆）：

`CLAUDE.md` → `ai/state/now.md` 顶部的 🔔 行 → `ai/roles/<你这一席>.md` → `ai/rules/` 四份 → **`ai/mail/to-<你这一席>/`（顺带查信）** → 手上那条任务。

**读完必须回四句话**：①这次**变了什么**（具体到条目）；②对我手上这条**有什么影响**；③我**接下来补做什么**；
④**顺手跑一次 `bash ops/verify/check-all.sh`，报「几红／点到我文件的是哪几条」，并报「信箱里有几封没处置」**——第④句是为了不靠人转告：**遗留的红躺在守门输出里、别席的话躺在信箱里，谁的文件谁自己查得出来**。

> **只回「好的，我已重新加载」＝ 没读。** 判据很简单：**它说不出变了什么，就是没读。**
> 这跟守门的道理一样——判「要保的那件事」，不判它的文本影子。
> **新开的会话不用**，它开场就会读到最新的这一份和 `now.md` 的 🔔 行。

### ※ 他说错人了：**接住，别照做，告诉他去找谁**

需求方常常对着手边那个会话直接说事——跟开发提需求、让审查写代码、让监督去开发。
**认出来并把他引到对的地方，是你的活，不是他的。**

**三件**：①说**后果**不说「规定如此」；②**明确告诉他去找谁、开场说哪一句**；
③**不替他转达**——转述会把目的丢掉，只剩表面动作。
🔴 **他坚持就照做**（需求方拍板 > 任何规矩），但**先说一句代价**，并在记录里写明「需求方要求，绕过 XXX」。

**五种越界各怎么回、以及「我该怎么开始」的完整答法**：`ai/rules/requester.md`。

**开发需求只跟审查者说。** 他说的每一件事（bug、要做的东西、问题、临时决定）
**先进 `product/requirements/inbox.md` 收件簿，一句一行，当轮记**——
一轮结束前 `待处理` 必须清零（`bash ops/verify/check-inbox.sh`）。

**跟维护者说的不是需求**——那是「这套模式该怎么改」，确认后进 `ai/rules/maintenance-log.md`，两条线不混。

## 三、七条铁律（全文 `ai/rules/laws.md`，违反哪一条都是白干）

1. **实现功能不是最高目标**——先审需求合不合理，复杂需求出 2~3 个方案比选，用到的技术先读一手官方文档和源码。（总纲，冲突时以它为准）
2. **开工前先查现成能力支不支持**——本项目选定的核心框架/平台能做的，一律优先用它，**读官方源码和文档，不是猜**。
3. **目标是「用它把系统做出来」，不是把它包一层**——它没有的能力，换设计或放弃，不要在外面再糊一层。
4. **审查和监督给的是意见，不是命令**——可以反驳，但要带依据（源码 / 官方文档 / 真机实测），三方地位对等。
5. **能自己做完的不要麻烦需求方**。
6. **给最优解，不是给「照做」**。
7. **一切结论带依据**：源码行号 / 实测数字 / 官方文档。「我觉得」不算。

## 四、目录一眼

`ai/` 四席协作的一切 · `product/` 产品定义（需求·设计·计划）· `docs/` 工程文档 · `src/` 源码 ·
`ops/` 部署运维与守门 · `dist/` 构建产物（不入库）· `claude-outputs/` Claude 草稿区 ·
`archive/` 历史（只进不出）· `tmp/` 临时（不入库，每段清空）。

**明细与「找东西去哪」在 `ai/index.md`**（全项目地图，紧接着这一份读）。
