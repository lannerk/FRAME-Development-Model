# 协作流程 · 三个角色怎么配合

## 一、一张图

```
需求方 ──说需求──▶ 审查者 ──整理──▶ product/requirements/specs/ ──▶ 开一条任务
   │                  ▲                                              │
   │                  │逐条核实                                      │待实施
   └──转产出──▶ 监督者产出                                           ▼
            claude-outputs/supervisor/                            开发者做
                                                                     │待审
                                       审查结论 ◀─────────────────────┘
                                   过 → archive/ ／ 打回 → 回到待实施
```

**唯一的真相载体是任务文件**：开发者和审查者**写同一个文件**。中间插新任务不影响老的；任何一方掉线，另一方从文件就能接上。

## 二、任务状态机

```
待实施 ──开发者认领──▶ 开发中 ──回报──▶ 待审 ──审查──▶ 已过 ──▶ tasks/archive/
   ▲                                      │
   └──────────── 打回（写明原因）◀────────┘

挂起：阻塞于需求方 / 真机 / 别的任务（「阻塞于」必须填清等什么、等到了谁来解锁）
作废：需求变了或被别的任务取代（写明被谁取代）
```

- 🔴 **推到 `待审` 之后立刻开下一单**——审查是**异步**的，别停下来等结论。
- **状态只有这六个**，不要自造。`过（带遗留）` 是**审查结论**不是状态：任务照样进 `已过`，
  遗留那部分**必须另开一条 `T-####`**，开不出来就是 `打回`。
- 改状态**同时改两处**：任务文件头 + `tasks/index.md`。
- `挂起` 没填「阻塞于」＝ `待实施`。等不到就转 `作废` 并说明，别挂着装样子。
- 已过的**满 3 段后**成批移进 `tasks/archive/`（按 `T-####` 原名平铺），索引里只留未结的。归档不是删：`grep -rl "T-0012" tasks/archive/` 随时找得回。

## 三、任务文件模板（照抄，字段一个都不要少）

```markdown
---
id: T-0042
标题: <一句话说清这条任务是什么>
提出: 审查者            # 审查者 / 需求方 / 开发者 / 监督者
类型: 开发              # 开发 / 顾问（顾问＝派给监督席的咨询单，见 §五之二）
派给: 开发者            # 开发者 / 监督者（顾问任务）
状态: 待实施            # 六个状态之一
优先级: P1              # P0 现在就做 / P1 本段 / P2 下段 / P3 有空 / P4 别忘
依据: AD<编号>
关联方案: ai/specs/<名>.md              # 定稿的技术方案，开工必读
关联原型: product/design/prototype/_PROJECT_/feature/<名>/   # 定稿的设计与图标，没有就写 —
关联bug: B-####                          # 这条任务要修的 bug，没有就写 —
关联里程碑: M-##                         # 属于哪个里程碑，没有就写 —
阻塞于: —
建档: 2026-09-16
更新: 2026-09-16
---

## 要做什么（审查者写）
一两句话说清目标与边界，不写实现细节。

## 怎么做（建议 · 可反驳）
审查者给的实施方式与依据。**开发者可以不按这个做**，但要在下面写清为什么。

## 验收（审查者写，开发者对着做）
- [ ] 可勾选、可验证，每条都能用命令或截图证明
- [ ] 不许写「功能正常」这种验收不了的话

## 开发者回报
- **做了什么**：
- **依据**：源码行号 / 官方文档 / 实测数字（三者取一，不许空）
- **实测**：真机上怎么验的、得到什么
- **自检输出**：自检清单（`ai/rules/conventions.md` §五，件数按项目定）跑完的结果（贴 `claude-outputs/developer/` 的文件名）
- **与建议不同之处**：改了什么、验证过程、为什么它的做法不合适（没有就写「无」）
- **修了哪些 bug**：`B-####`（一个都没修就写 `无`）。**填了这一行，审查席本轮必须复测**
- 🔴 **为什么停在这里**（**回报的最后一行，必须有**）：只许填四种之一——
  **①要需求方拍板** · **②要真机／条件而手上没有** · **③再做下去会让人断网或丢数据** · **④设计自相矛盾，做了也是错的**。
  队列里还有能做的单子却停了，**填不出这四种里的哪一种，本身就是打回理由**。填「这一单做完了」不算——那是交单，不是停。

## 自测（开发者写，推 `待审` 之前必须有）
- **构建对账**：从**仓库整棵树**重新构建一次，**产物的哈希必须等于测试机上正在跑的那一份**；对不上＝有东西没写回仓库，当场找。**逐文件对哈希只咬得住「已经想起来要写回的那几个」**，这一条咬得住「忘了写回」整类。（构建要可复现：去掉构建路径、时间戳这类会让两边永远对不上的东西。）
- **功能**：「验收」逐条走的结果（每条 通过／不通过）
- **UI 一比一**：对着 `关联原型` 比了哪几项、四态与窄屏深色看了没有、截图在哪
- **周边**：碰过的公共依赖还有谁在用、点了没有
- （没有界面的任务写「本条无 UI」，不许整节留空）

## 审查结论
- **第 N 轮（日期）**：过 / 过（带遗留，附 `T-####`） / 打回。打回写清哪一条、为什么、怎么改。

## 测试结论（审查者写；需求方说「审查并测试」时才有）
| 类别 | 结果 | 依据 / 为什么没测 |
|---|---|---|
| 功能 | | |
| UI 验收 | | |
| 接口 | | |
| 端到端操作 | | |
| 性能 | | |
| 用例覆盖 | | |
| 回归 | | |
| 全量 | | |
```

> 手段怎么定见 `ai/specs/testing.md`（审查席制定并维护）。**八行一行都不许空**——
> 没测的写清为什么没测，**空着等于没想过**。

## 三之二、bug 怎么走

bug 和任务是两本账：**bug 记「坏了什么、怎么重现」，任务记「谁去改、改成什么样」。**
一条 bug 在 `ai/bugs/B-####-<一句话>.md`，修它的活在 `ai/tasks/T-####`，两边互相指。

**四条不许**：①**复现四件**（环境 / 前置条件 / 步骤 / 现象）没写全，不许转给开发；
②开发**不许自己标 `已关闭`**，关闭权在审查席；③回报里「修了哪些 bug」非 `无`，
**审查席本轮必须复测**，不挂在「审查并测试」口令上；④需求方报的 bug，**审查席先自己复现一次**，
复现不了标 `待复现` 回去要条件，**不许丢给开发猜**。

**bug 文件模板、四种来路、状态机、定位节怎么写**：**`ai/bugs/README.md`**。


## 三之三、规范中途改了，在途的任务怎么算：**不追溯**

**判据是时间，不是道理**：任务推到 `待审` 的时间 vs 规范文件改动的时间。
**规范比交付晚的，不许拿新规矩打回**——开发不可能按一份还不存在的模板写东西。

🔴 **时间看 git 提交时间，不看 mtime**（2026-09-15 改，理由见 `ai/memory.md` 第 8 条）：

```
git log -1 --format=%cI -- ai/rules/workflow.md     # 规范这一份最后一次提交的时间
git log -1 --format=%cI -- ai/tasks/<任务>.md     # 交付那一条的时间（推 待审 那一次提交）
```

**mtime 是文本影子**：`git clone` 一次、换台机器、跑一次 CI，全部文件的 mtime 都变成签出时刻，
**「谁早谁晚」当场失效**（实测过：新克隆里所有文件相差几毫秒）。还没提交的改动按「现在」算。

| 情况 | 怎么办 |
|---|---|
| 规范**晚于**交付，缺的是**字段 / 章节** | **审查席直接补**（它本来就能改文档），并在任务里注明「规范晚于交付，字段由审查席补，**不计入结论**」 |
| 规范**晚于**交付，新规矩改变了**做法** | 这一条**按旧规矩审**；新做法另开一条任务，写明依据 |
| 规范**早于**交付，开发没照做 | 正常打回 |
| **例外：新规矩是为了堵一个正在发生的事故**（安全、数据会丢） | **追溯**，并在任务里写明为什么这一条要追溯 |

**下一条任务开始按新规矩全套来。** 不追溯不等于不生效。

> **维护席那边的配套**：改完规范，`ai/state/now.md` 顶部的 🔔 行要写**日期**，
> 让「谁早谁晚」有据可查，而不是靠谁记性好。

## 三之四、这条任务要动**别席的文件**怎么办

§七 那张归属表管的是「**谁维护、红了归谁、谁提交**」，**不是「谁许可动」**。
需求方拍板的任务单可以派一席去动另一席的文件——效力顺序摆在那儿。所以两头各有一个动作：

| 谁 | 什么时候 | 做什么 |
|---|---|---|
| **开单的那一席** | 开任务之前 | 对一遍 §七，**在单子里写清「哪几个文件归谁」**；跨了席就在「要做什么」里点名 |
| **做活的那一席** | 发现跨了席 | **按单子做，不停**（停在这儿等裁定＝让那个坑再躺一轮），但**当轮发信给归属席**：动了哪几个文件、为什么、哪几件是超出单子的 |
| **归属席** | 下一轮查信 | 复核，不对就改回去，结论写进归档那一行（`ai/mail/README.md`） |

🔴 **这三种动作必须发信**，漏一个就等于**改了账没人知道**：①动了 `ai/template/*` / `ai/template-en/*`；
②跑了 `check-template-sync.sh --accept`（它改 `ops/verify/.sync-state`，那是**全体模板同步的账**，不是你这一轮的东西）；
③新增或改写了 `ops/verify/*` 里的守门。

**本模板的来源项目实测**：一张单子四件事里三件归维护席，做活那一席照单做完、当轮发信报备，
归属席下一轮复核并订正了两处（模板只同步了一份语言 · 脚本把本项目的文件名前缀写死了）。
**跨席本身不是错，不报备才是。**

## 四、需求方的输入怎么进来

1. 原话**一字不改**存 `product/requirements/verbatim/<日期>-<一句话>.md`。
   为什么留逐字：复述会丢东西。吃过亏——「多段切割上传」被复述成「只是传得可靠」，把它真正的目的（让 AI 自己能传）丢了。
2. 审查者整理成可验收的规格 → `product/requirements/specs/<功能>.md`。
3. 要拍板的做成**选择题**（两三个选项 + 各自代价 + 推荐与理由），**用弹窗控件弹给他**（见 §四之二）。
4. 拍板结果记一条 AD，并标明**「需求方拍板」而不是「代拍」**——开发见到这句就不用再问。
5. 他在一轮进行中插话：折进当前这一轮，把给开发的那份**重写成完整版**（开发只读最新一份）。

## 四之二、怎么跟他打交道：**整块在 `ai/rules/requester.md`**

三条，细则在那一份：

1. **要他拍板就用弹窗选择题**，不许把 A/B/C 排在正文里等他打字；推荐项第一并标（推荐）、每项写代价。
2. **不要只照做**——能推断出更好的就提出来让他确认（**先把他要的办了，再说还有几种可能，每条写代价**）。
3. **他说错人了**：接住、别照做、告诉他去找谁开场说哪一句；**他坚持就照做**，但先说代价并留痕。


## 四之四、他问「还有什么要做 / 还有什么 bug」：**按他问的范围列**

这种问题随时会来，**答案必须从台账里捞，不许凭记忆**——记忆会漏，而漏掉的那条正是他在意的那条。

**四本账，各管一段**：

| 他问的 | 去哪捞 |
|---|---|
| 还有什么要做 / 进度到哪 | `ai/tasks/index.md`（未结的那些） |
| 还有什么 bug | `ai/bugs/index.md` 的「在办」表 |
| 我上次说的那件事呢 | `product/requirements/inbox.md`（连 `不做` 的也要能报出去处） |
| 当初为什么这么定 | `ai/decisions/`（按号段文件查，别通读） |

**「按范围」是这件事的关键**——他很少要全量。先认出他划的是哪种范围，再过滤：

| 他这么问 | 你按什么筛 |
|---|---|
| 「**还有什么急的**」 | 优先级 P0/P1 |
| 「**VPN 那块还剩什么**」 | 功能 / 模块 |
| 「**有没有严重的 bug**」 | 严重度 S1/S2 |
| 「**卡住的有哪些**」 | 状态 `挂起` + 写清阻塞于什么、等谁解锁 |
| 「**我上周说的那些**」 | 时间段（收件簿有日期） |
| 「**开发手上在做什么**」 | 状态 `开发中` / `待审` |
| 「**这一版还差什么**」 | 该版本关联的任务 + 未关闭的 bug，**两本一起报** |

**报的格式（四样，一样都不少）**：

1. **先给总数与范围**：「你问的是 VPN，未结 6 条 + bug 2 条」——**他先要知道有多大**；
2. 每条一行：**编号 + 一句话 + 状态 + 卡在哪**（不卡就写在谁手上）；
3. **按他的范围排序**（问急的就按优先级排，问模块就按模块聚）；
4. 末尾一句**你的判断**：先做哪条、为什么。他要的是判断，不是清单。

**三条不许**：

- **不许漏掉 `挂起` 和 `不做`。** 他问「还剩什么」，被你判成不做的那条**也是答案的一部分**——
  他有权推翻你。悄悄扣下来，下次他发现时丢掉的是信任。
- **不许只报任务不报 bug**（反过来也一样）。**「还有什么要做」天然包含「还有什么坏着」。**
- **不许给一个对不上的数。** 报了「6 条」，台账里就要真的是 6 条；
  **数不对的时候先去对账，别先回话。**

> 范围听不懂就**先确认范围再答**——「你是问整个项目，还是只问 VPN？」
> 这是唯一该反问的时候；其他时候他要的是答案。

## 四之五、产出怎么交给他：**送到他手上，别报路径**

需求方原话：「例如你这个『报告写好了：`claude-outputs/supervisor/xxx.md`』，**我又要打开文件夹去找**」
／「**以后输出的文件，都能显示出来让我点击在右边查看预览，按规范放在什么位置没问题**」。

**注意后半句**：文件**照规矩放**（那是我们的事，他不管），他要的是**不用离开这段对话就能看到**。

任何一席产出文件——报告、方案、审查记录、复盘、截图、对比图、步骤单——
**必须在同一条回话里让他能直接点开看**。仓库路径只作为归档记录写在旁边，**不能当交付**。

**不许只给一行路径。** 那等于让他去翻文件夹，而且他手上可能根本不是那台电脑
（他在手机上、在别的机器上、或者那台机器正好卡着——这一轮就发生过）。

**怎么送，看你这个会话所在平台给了什么能力**（把文件送进对话、生成可预览的页面、附件……）：
平台不同做法不同，**但判据只有一个，且不随平台变**：**他不用离开这段对话，就能看到内容。**

配套三条：

1. **送文件 + 三句摘要**，不要把全文再贴一遍到对话里——他要么看摘要决定要不要点开，
   要么直接点开看全文，**两份一样的内容只是在烧他的注意力和 token**。
2. **文件名照旧 `<日期>-<一句话>`**——他在列表里一眼要能认出是哪一份。
3. **改过之后要重新送一次。** 他手上那一份是你上次送的那个版本；你在仓库里改了而没重送，
   他看的就是旧的，**而且他不会知道**。

## 五、监督者的输入怎么进来

`claude-outputs/supervisor/`（原样入库，任何人不改一个字） → 需求方转给审查者 → **审查者逐条核实** →
核实记录放 `claude-outputs/reviewer/` → 成立的转任务/AD，不成立的写明否掉的依据。

**冲突只进核实记录，不进给开发的任务文件。** 开发不需要知道三方谁对谁错，只需要知道最后定的是什么。

## 五之二、顾问任务（咨询单）—— **审查席自己定的东西，怎么被独立看一眼**

**这条解决的是一处闭不上的分权**：架构、数据库、技术选型、UI 规范这几样，
**是审查席定的**；它的实现又是**审查席审的**；过不过也是**审查席判的**。
同一个席位定标准、判达标，中间没有第二双眼睛。

**需求方拍板的解法**（原话逐字在 `ai/rules/maintenance-log.md`）：

> 「审查者给的所有方案或结论……我可以直接拍板过，但是我如果说需要咨询监督之类的话，
> 审查者会派单给监督一个顾问任务，我再去和监督说继续或查看任务之类的，他就会读到并给意见结论，
> 回到审查者这边，我只要说监督已经给出意见，审查者就能读到，并结合意见再给结论」

**关键是「按需触发」，不是每条都加一轮。** 默认你直接拍板；**只有你开口要咨询**，才走下面这条。

### 怎么走（五步）

| # | 谁 | 做什么 |
|---|---|---|
| 1 | **需求方** | 对审查席说一句「**这条我要咨询监督**」 |
| 2 | **审查席** | 开一条**顾问任务**：`ai/tasks/T-####`，`类型: 顾问`、`派给: 监督者`。**用现有的任务账本，不另开一本。** 任务里写清：要它看什么、有哪些已知约束、**你希望它重点质疑哪一点** |
| 3 | **需求方 → 监督席** | 说一句「**看任务**」或「继续」 |
| 4 | **监督席** | **只读派给自己的那一条**（见下），给意见与结论 → 写进 `claude-outputs/supervisor/<日期>-<一句话>.md`，并在任务文件里留一行指过去，状态推 `待审` |
| 5 | **需求方 → 审查席** | 说一句「**监督已给出意见**」→ 审查席读那份产出，**结合它再给结论**，然后关掉这条顾问任务 |

### 三条硬规矩

- **监督席读队列的唯一例外就在这里**：需求方说「看任务」时，它可以
  `grep -l '派给: 监督者' ai/tasks/T-*.md` 找到自己那条，**只读那一条**。
  **不许顺带看别的任务，不许由此开始排期**（`ai/roles/supervisor.md` §一）。
- **关闭权在审查席**（它是派单人）。监督席只能推到 `待审`。
- **审查席可以不采纳**——但**必须在任务里写明为什么否掉，带依据**。
  这是残余风险：独立的眼睛看了，采不采纳仍在审查席手上，**最终兜底的是需求方**。
  所以第 5 步之后那条结论，**你可以直接推翻**。

> **为什么不做成「每条 AD 强制加一轮监督」**：那会把每个技术决定都变成两轮，
> 成本翻倍而多数决定根本没有争议。**按需触发**把成本花在你真正不放心的那几条上——
> 代价是：**你不开口，就没有第二双眼睛**。这一点要说清楚，不藏着。

### 复盘材料不由被审的那一席自己总结

**原始材料**（原话逐字 + 时间线，不做评价）由被审那一席出，**入库 `claude-outputs/<席>/`，不许放 `tmp/`**；**评价由监督席出**，走 §五之二 咨询单。**为什么**：自评站在席位里写，**结构上看不见一整类问题**（实证见 `claude-outputs/README.md`）。

## 六、优先级

| 级 | 什么 | 什么时候做 |
|---|---|---|
| **P0** | 正在让系统不可用（整块功能打不开、数据会丢、提权） | 插队，当天 |
| **P0** | 安全（权限、密钥、注入） | 插队，当天 |
| **P1** | 需求方当面提的 bug 与小需求 / 已排期的功能 | 本段 |
| **P2** | 已排期但不挡人的 | 下段 |
| **P3** | 技术债、重构——**穿插着做，随时可停** | 有空 |
| **P4** | 账目卫生、存量核对 | 记着别忘 |

**挂起的不占优先级**——它等的是外部条件，不是排在谁后面。

## 七、每段收尾开发者必做四件（**一段可以装好几单**）

🔴 **「推一个单子进 `待审`」不等于「这一段结束」。** 这四件是**一段只做一次**的收尾，不是每交一单做一次。
交出去之后**立刻开下一单**——审查是异步的，它审它的，你做你的。
**什么时候才算一段结束**：派给你的单子全部推走了，或者你撞上了「为什么停在这里」那四种之一。
（本模板来源项目实测：规矩之间留了这道缝，开发席推完一单就收尾，后面排着的三单一单没动——
**两句话各自都对，合起来就停早了**。）

1. 更新 `ai/state/now.md` 被这段改动的段落。
2. 把这段动过的**每一条 AD 的「实现」列改掉**（在 `ai/decisions/` 对应号段文件里，一条都不要漏）。
3. 任务状态推到 `待审`，回报五小节 + **「自测」一节**写完；自检**原始输出**与自测截图贴进 `claude-outputs/developer/<日期>-自检.md`。
   **自测没过不许推 `待审`。**
4. 写一行 commit message 放进 `state/now.md` 末尾，需求方提交时直接复制。

四件缺一件，下一段接手的人就得自己翻代码重建现状——那比写这四件贵得多。

## 七之二、提交 · 回写 · 巡检（**整节在 `ops/README.md`**）

三条规矩，细则和命令都在 `ops/README.md`：

1. **谁改完谁提交**：审查席一轮结束提交、**维护席改完规范自己提交**、**开发席不提交**
   （自己写的自己提交＝绕过审查）。跑 `bash ops/scripts/commit-round.sh "<标题>" --seat <你这一席>`（**归属表在 `ai/rules/layout.md` §七；横跨两席脚本会停下**），
   **只 add + commit，永不 push**；**守门红着不许提交**；**SourceTree 安全五不许**。
2. **真机改完必须回到仓库**：同轮写回 + `sha256sum -c` 对账。四级办法都不行就挂账
   `tmp/writeback-pending/`，**挂着不算交付完成，审查席不许判过**。
3. **`规范巡检`**：需求方觉得跑偏了，维护席跑 `bash ops/verify/check-all.sh`，**只回一张表**。
