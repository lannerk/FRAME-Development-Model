# bug 怎么走 —— 闭环，谁都不许断在中间

> 这一节原本在 `ai/rules/workflow.md` §三之二，因为那份涨过了预算，整节挪到这里。
> **规矩没变**，只是搬到了它管的东西旁边。索引在 `index.md`，一个 bug 一个文件。
>
> **动手查之前先读 `ai/rules/investigate.md`**（头一小时手册，五步）——**开发席和审查席都要读**。

🔴 **bug 上的一切来往写在这条 bug 文件里，不走信箱**（现象 · 复现 · 定位 · 修复 · 复测 · 返工）——**开发席与审查席之间基本上不需要互相发信**；信箱只传跟具体 bug 无关的话（`ai/mail/README.md`）。
bug 和任务是两本账：**bug 记「坏了什么、怎么重现」，任务记「谁去改、改成什么样」。**
一条 bug 在 `ai/bugs/B-####-<一句话>.md`，修它的活在 `ai/tasks/T-####`，两边互相指。

### bug 文件模板（照抄，复现四件一个都不能少）

```markdown
---
id: B-0007
标题: 打开设置面板后返回，列表空了
严重度: S2                 # S1 阻断 / S2 严重 / S3 一般 / S4 轻微
来源: 审查席测试            # 审查席测试 / 需求方 / 开发席 / 监督席
状态: 已复现                # 待复现/已复现/待修/修复待复测/已关闭/无法复现/不修
关联任务: T-0042           # 没有就写 —
发现: 2026-09-15
关闭: —
阻塞于: —                  # 只有「修复待复测」能写；等的是什么**外部条件**（真机、硬件、需求方的动作）
解除人: —                  # 谁能把那个条件变出来。两行要么都写、要么都不写
---

## 复现（**四件缺一条就不许转给开发**）
- **环境**：机器 `<machines.json 里的 id>` / 版本 / 分支 + commit
- **前置条件**：什么账号、什么数据、哪些开关、网络什么状态
- **步骤**：1. … 2. … 3. …（**别人照着走就能再现**，不许写「操作了一下」）
- **现象**：期望 `<…>`，实际 `<…>`；附截图 / 日志 / 请求响应
- **复现率**：3/3 还是 1/5（**偶发的必须写清楚**，否则开发会以为自己修好了）

## 定位（审查席写，可以为空）
读到哪一层、怀疑哪里，**带行号或实测**。没把握就留空，别写猜测当结论。

## 修复（开发席写）
- **根因**：为什么会这样。**不许写「加了个判断」**——那是手法，不是原因；
  **同理，绕法（换个窗口 / 无痕 / 换端口）也不是根因**——它回答「现在怎么先用着」，不回答「为什么会这样」
- **改了什么**：文件 + 行号
- **自测**：按上面的「步骤」原样重跑一遍的结果

## 复测（审查席写，**只有这一节能关闭它**）
- **第 N 轮（日期）**：按原步骤重跑 → 通过 / 不通过
- **顺带回归了什么**：这次改动碰的公共依赖，还有谁在用
```

### 四种来路，四种走法

| 来路 | 审查席要做的第一件事 |
|---|---|
| **审查席自己测出来的** | **当场开 B 号**，复现四件写全。写不全说明你自己也没测清楚，回去补 |
| **需求方报的** | 先进收件簿（一句一行），**然后你自己先复现一次**。复现得了 → 写全四件转 `已复现`；**复现不了 → 开 B 号标 `待复现`，回去问需求方缺什么条件**（哪台机器、什么账号、第几步），**不许把没复现的 bug 丢给开发去猜** |
| **开发席自己发现的** | 让他开 B 号（`来源: 开发席`），不擅自扩大当前改动 |
| **监督席提的** | 按 §五 逐条核实；**核实的方式就是复现一次** |

### 交给开发的时候，他必须能拿到三样

任务文件里填 `关联bug: B-####`，开发**开工前读那个文件**。他从那里拿到：
**有什么 bug（现象）、怎么还原（步骤）、什么条件下会出（环境 + 前置条件）。**
**这三样里缺一样，这条任务就不该派出去。**

### 开发回报要多写一行

回报里加 **`修了哪些 bug:`**，填 `B-####`（一个都没修就写 `无`）。
修完把那条 bug 推到 `修复待复测`，**不许自己标 `已关闭`**。

### 复测是自动触发的，不用需求方开口

**只要开发回报里的「修了哪些 bug」不是 `无`，审查席本轮就必须复测那几条**——
按 B 文件里的原步骤重跑，**不需要需求方说「审查并测试」**。
复测过了才把 bug 推 `已关闭`并登记进台账的「已关闭」表；没过就退回 `待修`，在同一个 B 文件里追加一轮。

### 🔴 复测真的做不了的时候：挂起，不是拖着

有一类 `修复待复测` 等的是**审查席无权解决的外部条件**——「装机盘真装一次」「需求方插第二根网线」。
这时候在表头把两行写全：

```
阻塞于: 等装机盘真装一次
解除人: 需求方
```

守门就把它列成 **⏸ 挂起、不计断口**，而不是和「没人复测」混在同一条红里。
**为什么要分**：旧判据下这条红永远在，而**永远在的红等于没有红**——久了谁都不看它，真的断口也跟着被盖住
（审查席 2026-09-23 实测：剩下的 14 条全是等真机的，于是它连 `--seat` 提交都被一条自己无权解决的红挡死）。

**三条边界，缺一条它就变成新的垃圾桶：**

1. **两行要么都写、要么都不写。** 只写「阻塞于」＝挂起无主，没人知道该去催谁——那正是它会烂在那儿的原因。
2. **只有「修复待复测」能挂起。** 待修就是还没修、待复现就是还没复现，那两种写「阻塞于」等于给自己开豁免。
3. 🔴 **挂起不是归档**：超过 **21 天**没动照样报红（`BUG_BLOCKED_MAX_DAYS` 可调），「没动」判的是
   **git 最近一次提交时间**（mtime 一次 clone 就全变了）。到期三选一：条件到了就复测 · 没到就去催解除人 ·
   催不动就改判「不修」并写清理由。

> **为什么复测不挂在口令上**：口令管的是「要不要铺开测」，
> 而「修过的东西到底修好没有」是**每一轮都必须知道的事**。
> 挂在口令上，就会出现「需求方没说测，所以没人知道它修好没有」——
> 那条 bug 会在两轮之后以「又出现了」的形式回来，而那时已经没人记得它原来的复现步骤。

## 「已复现」不等于「知道根因」

**`已复现` 只说明你能让它再现一次。** bug 文件**允许、并且鼓励**这个组合：
**状态 `已复现` + 根因 `未定`**。这时候开的任务是**调查任务**（「查清 X 的根因」），不是修复任务。

**不许为了给个交代，把一个只解释了一半现象的机制写成根因。**
判断标准很简单：**把现象逐条列出来，你的机制解释不了其中任何一条，就是「未定」。**
真事：「整个浏览器不动」和「请求一直转圈」是两层，**一个机制只解释了后者，就不能签前者的字**。

## 绕法（workaround）不是调查结果

绕法**只能写在「## 临时缓解」小节**，**不许出现在「下一步」**，
**也不许作为把状态往前推、或者把严重度往下降的理由**。
需求方原话：「**只叫我用无痕模式就能绕过，本身绕过就不是解决 bug 本身的调查需要的东西，
而是想办法复现或者预测可能情况是怎么样**」。

## 「定位」节固定三个小标题

```
### 能不能本地复现      ← 头一小时手册第 2 步的三问，答案必须是其中之一
### 排除树              ← 至少两支，每支写【怎么判掉 · 要多久 · 结果】
### 结论或当前假设      ← 所有分支都有结果才许写「结论」
```

**前端类 bug 的「能不能本地复现」必须贴复现台的输出**，或写明为什么它不适用。

## 审查席在这条线上的位置（从 `reviewer.md` §6.4 搬来）

测出来的问题**当场开 B 号**（`ai/bugs/B-####-<一句话>.md`），**复现四件写全**：
环境 / 前置条件 / 步骤 / 现象。**写不全不许转给开发**——他拿不到还原条件，修的就是另一个问题。

- **需求方报的 bug**：先进收件簿，**然后你自己先复现一次**。
  复现得了才转 `已复现` 开任务；**复现不了就标 `待复现`，回去问他缺什么条件**（哪台机器、什么账号、第几步），
  **不许把没复现的 bug 丢给开发去猜**。
- **交给开发**：任务里填 `关联bug: B-####`，他开工前会读那份文件。
- **复测是自动的**：开发回报里「修了哪些 bug」不是 `无`，**你本轮就得复测**，
  按 B 文件的原步骤重跑，**不用等需求方说「审查并测试」**。
- **关闭权只在你这里。** 开发只能推到 `修复待复测`。复测过了你才推 `已关闭`并登记台账；
  没过退回 `待修`，在同一个 B 文件里追加一轮。
- 已关闭的那批**就是回归清单**，每轮重跑（§6.2 第 7 条）。

详细走法与文件模板见 `ai/rules/workflow.md` §三之二。
