# 分域做法：应用与插件生态

> 做任何「能装应用 / 插件 / 扩展」的产品都照这套想。

| 维度 | 做法 | 为什么 |
|---|---|---|
| 协议通用 | 一套应用与插件协议，**core + profile**：通用部分一份，不同产品只扩展字段（`<base>.plugin/1` + `<product>.app/1`） | 下一个产品不用重新定义插件 |
| 安装引擎 | 一个抽象层统一处理安装 / 卸载（含「假装」安装，便于测试）、对接内核接口与应用权限 | 各种来源的包走同一条路 |
| 分类 | 按「界面是谁写的」分：插件应用（用我们的组件写，可带容器后端）· 容器应用（界面是容器自带）· 纯资源包（风格 / 布局 / 语言 / 屏保 / 技能，**无进程、无可执行代码**）；插件可以完全没界面 | 分类决定了审核和沙箱强度 |
| 一份动作定义 | 应用声明 `actions`，**一份生成 HTTP / CLI / MCP 工具 / 界面按钮 / 流程步骤** | AI 和人走同一条通路，不会一边能做一边不能做 |
| 投影与扩展槽 | 应用往系统投影：窗口 · 增强（实现宿主已有的位置，例如长在某个设置页侧栏）· 菜单 · 文件处理者 · 小组件 · 浮层；扩展槽有 JSON Schema，**加槽随时可以，减槽不行** | 宿主和应用各自演进不互相打断 |
| 功能与互斥 | 依赖写「功能」不写应用 id；同一功能多个实现都能在商店装，但只能装一个——互斥由基数算出来 | 用户能换实现，系统不会装出两个冲突的 |
| SDK 能力 | 任务（进度 / 暂停）、通知、网络事件、设备插拔、日志、AI 能力（含聊天卡片）、语音、个人数据与备份、缓存清理、摄像头麦克风权限、任务栏菜单、应用更新 | 第三方最常要的就是这些 |
| 对外服务 | 应用可对外提供 HTTP / MCP / SSE，由系统统一做加密、鉴权、限流、审计；**开放公网只能由管理员部署后打开**，不能写死在包里；来路按凭据分域 | 应用作者不该决定用户的暴露面 |
| 协议增强代理（预留） | 对外暴露标准协议端口（数据库 / 对象存储 / 缓存 / 消息），中间由插件做优化、缓存、审计、脱敏 | 老客户端不改就能享受增强 |
| 生态阶段 | 内置全按标准协议写 → 第一个可安装应用 → 纯资源包开放第三方 → 带后端的第三方上架（签名、审核、分档兼容）→ 付费与订阅 | 风险从低到高逐级放开 |
| 零代码供给 | 风格包、技能包是普通用户或 AI 就能产出的东西 | 生态的第一批供给不必等专业开发者 |
| 命令行 | 一个薄壳命令行 + `invoke <应用> <操作>`；应用可自带排障命令行，但 **AI 不直接执行应用自带命令行**；命令树可被宿主挂成别名，协议 id 不别名 | AI 只走有权限与审计的通路 |
