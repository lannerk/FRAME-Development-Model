# 分域做法：UI 框架、组件库与系统界面

> 做组件库、设计系统、或有复杂界面的产品时照这套想。**做普通应用只取需要的几行。**

## 组件库

| 维度 | 做法 | 为什么 |
|---|---|---|
| 范围 | 像主流后台组件库那样一整套：基础组件 + 图表 + 图标 + 组合组件；每个组件有属性 / 事件 / 方法 | 用的人不想再拼第二个库 |
| 流程 | 契约 → 自研实现 → 第三方适配 → 一致性测试 → 文档页；**一份逐项完成清单 + 台账**，清单加步骤时回补旧组件 | 没有清单，后做的组件和先做的组件质量不一 |
| 顺序 | 第一个简单组件做样板，然后**先做最难的**（组合框、日期选择、表格）验证引擎 | 难的组件最能暴露架构问题，越早越便宜 |
| 框架 | 给别人用的库考虑 React / Vue / Svelte 同步；契约去框架化 | 使用方的框架不由你定 |
| 第三方适配 | 只认官方出品；一个库同时支持几个框架就都适配 | 非官方封装常停更 |
| 构建与脚手架 | 各框架主流构建（Vite / Next / Nuxt / SvelteKit / webpack）；自己的脚手架选框架后过滤可选适配库；TS 与 JS 都支持 | 下游开发者第一眼看到的是脚手架 |
| SSR | 能做前端网站：无闪烁、无水合差 | 官网类用户一定会问 |
| 主题 | 多风格包可切换、可安装、可由 AI 生成；风格 × 外观（浅 / 深 / 高对比）× 密度 × 动效 × 方向正交 | 正交才不会组合爆炸 |
| 定制 | 对齐主流库的全局配置：运行时改令牌、种子色派生、组件级令牌、嵌套局部配置、全局默认值；能基于内置风格再覆盖 | 用户最常见的需求是「只改一点点」 |
| 国际化 | 语种对齐主流库、按需加载、RTL；**宿主的 i18n 能整合成一个语言源** | 两套语言源一定不同步 |
| 人看文档 | 全局指南 + 每组件一页 + **组件总览页** + **在线案例**；大版本并存；多语言 | 这是用户判断「能不能用」的地方 |
| AI 用的东西 | 分层检索：总览 → 索引 → 条目；skill / MCP / CLI 同源；带版本号（没指定取项目已装版本，再不行取最新）；英文 | 一次灌进上下文既贵又不准 |
| 随做随补 | 框架、组件、适配、国际化、文档在开发过程中逐条补齐，最后只梳理 | 最后补 = 永远补不完 |
| 预留 | 动画、特效、画板、组合组件（带计划面板的 AI 聊天、窗口控制）先登记接口 | 以后加不用改契约 |

## 系统界面（做桌面 / 平台类产品时）

| 维度 | 做法 | 为什么 |
|---|---|---|
| 四维正交 | 风格包 × 外观模式 × 透明度 × 布局 | 每维独立换，组合自动成立 |
| 布局 | 桌面可有多套（传统多窗口 + 单窗口）；应用与文件界面一套自动适配；第一版至少两套风格 × 两套布局 | 两套才能证明真的正交 |
| 风格包 | 可安装、可上传（名称与描述不必多语言；列表与详情带预览小窗）、可由 AI 提示词生成；**只能改外观，不能改位置与存在**；包里不许有可执行代码 | 风格包是生态的第一批零代码供给，也是安全边界 |
| 样式契约 | 组件里不许出现字面样式值，只许 `var(--*)`；CSS 只用逻辑属性 | 机器能验；风格包才有意义 |
| 组件只有一份 | 所有界面都基于同一套组件（含布局组件）；不够就加，组件库进应用 SDK | 第三方和内置长得一样 |
| 组合组件 | 高频组合（进度条 + 可展开终端日志等）做成组件 | 避免每个应用各写一版 |
| 小组件面板 | 应用注册小组件（数据 / 开关 / 进度 / 跳转），拖动排序、多页，手机端同一份 | 一眼总览 |
| 系统级 | 通知中心、卡片通知、屏保与电源、恢复模式页、设置向导 | 这些缺了就不像一个系统 |
| 视觉特效层（预留） | 背景、开机、登录、AI 反馈的特效；**装饰不是组件：关掉它界面照常可用**；有性能预算与降级阶梯 | 低端设备也要能用 |
