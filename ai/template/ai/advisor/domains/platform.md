# 分域做法：平台 / 操作系统 / 设备类产品

| 维度 | 做法 | 为什么 |
|---|---|---|
| 产品线 | 一个品牌、几条线：满血形态 · 轻量形态 · 多端客户端（存在的理由是连多台设备）· 云端（官网 · 商店 · 账号 · 开发者平台 · 对外 API · 远程控制面）· 管理后台 | 先画全景，才知道哪些东西要共用 |
| 满血与轻量 | 同一个产品两个形态：共用内核、应用协议、SDK、界面、权限表；平台差异收在 Provider 层，**按「功能」切**，不做通用 Linux 适配层 | 通用适配层会把满血形态的能力削成最小公约数 |
| 架构与镜像 | 应用开发者基本不管 CPU 架构，镜像按架构分别打；轻量形态只做 arm64 与 x86_64 | 32 位与冷门架构的测试成本远大于收益 |
| 排期 | 第一阶段：系统本体 + 全部内置应用 + 扩展性；之后**按技术依赖排**（轻量形态 → 客户端与远程 → 云端 / 后台） | 按依赖排就不会做到一半回头补底座 |
| 远程访问 | P2P 直连为主；用户可自建中继；官方兜底中继严格限流、界面明说；寻址从第一天带设备 id（`<scheme>://<设备>/<应用>/<资源>`） | 数据不经过我们；以后加多设备不改 URL |
| 授权激活 | 授权是签名文档；在线 / 离线 / 远程三条激活路径；授权与权限两套字段 | 离线设备也要能激活 |
| 错误收集 | 让用户选是否上报；服务端汇总、自动回复；缺陷直接回流开发队列；用户报告与缺陷分权 | 线上问题要能进开发闭环 |
| 调试通道 | 本地维护开发有标准的维护、调试通道，AI 能自动推送、验证、测试 | AI 开发时最缺的就是「能在真机上验证」 |
| 系统基线 | 可回滚文件系统（快照）、签名的软件源、升级前自动快照；Wayland | 升级失败能一步退回 |
| 进程与安全 | 内核进程不以 root 跑；特权只走**类型化动作**的特权助手（没有通用 exec）；每用户代理；应用各自沙箱，只走 unix socket | 一个 exec 口子就是整台机器 |
| 状态 | 真值在内核；全局状态同步（先 list 再 watch，带版本号）；一个客户端一条事件连接、断线续传 | 多界面、多设备看到同一份真值 |
| 专业应用（预留） | 视频剪辑这类要用的底层先留位：GPU 编解码、大文件流式读写、长任务渲染、专业组件 | 以后做不用改内核 |
| 开发运维（预留） | CI/CD 对接各种 git；服务器面板（部署应用、统一对外出口、域名证书与自动续签）；打包构建在独立沙箱 | 平台自己就是开发者的工作台 |
| 家庭 / 设备生态（后置） | 先做最会「看」的中枢 → 设备领域抽象层 → 标准协议控制端（如 Matter Controller）→ 设备身份 PKI → 语音终端 + 中枢大脑 → 认证计划；**领域层不许出现协议名与品牌名** | 协议会换，领域不会 |
| 边界 | 写清不做什么品类（例如不做手机系统、不做电视系统） | 平台类产品最容易被拖着扩张 |
| 不可逆清单 | 写代码前列出（进程模型、状态模型、寻址、授权、样式契约、文件系统……），逐条拍板 | 平台类产品的不可逆决定特别多 |
