# 选型卡

> 每张卡：**情况 → 推荐 → 为什么 → 什么时候不适用 → 可反悔点**。
> 这是「没有别的约束时」的推荐，画像里有定法以画像为准；选别的要说清为什么。
> 🔴 版本一律查当天最新稳定版，**实现前读该版本官方文档或源码**——卡里不写版本号，就是为了不让人照抄旧版本。

---

### 后端语言
- **情况**：设备端服务、要装在各种机器上、要交叉编译、希望装卸干净。
- **推荐**：**Go**，核心部分只用标准库。
- **为什么**：单个二进制，没有运行时要装；交叉编译几乎零成本；标准库就能写 HTTP、JSON、SSE；不引依赖就没有依赖冲突，多个模块放在同一个仓库也不打架；契约的类型设备端和云端可以直接 import，不靠代码生成。
- **不适用**：以 Web 为主、团队只会 JS → **Node + TypeScript**（前后端一种语言、类型共享）；数据分析 / 机器学习为主 → **Python**；极致性能与内存安全、愿意付学习成本 → **Rust**；企业既有 Java 体系 → **Java / Kotlin**。
- **可反悔点**：对外只暴露 HTTP / CLI 契约，内部语言可以按模块换。

### 前端框架
- **情况**：开发主要靠 AI、要和官网 / 后台共用组件。
- **推荐**：**React + Vite + TypeScript**。
- **为什么**：AI 写 React 最稳（训练语料最多）；生态最大；官网、后台、客户端能直接 import 同一批组件。
- **不适用**：团队熟 Vue → Vue；追求极小体积 → Svelte；做给别人用的组件库 → 考虑 React / Vue / Svelte 三框架同步，契约去框架化。
- **可反悔点**：组件契约不绑框架，就能加框架。

### 无头组件层（可访问性）
- **推荐**：React 用 **React Aria**；Vue / Svelte 用 **Zag.js**。
- **为什么**：焦点管理、键盘操作、ARIA、从右到左都内建，这些自己写一定写错。
- **可反悔点**：包在自己的组件里，外面看不到。

### 样式方案
- **推荐**：**CSS Modules + 设计令牌**（`var(--*)`），用 stylelint 限制「只许令牌」；CSS 用逻辑属性。
- **为什么**：主题 / 风格包 / 深色模式都靠令牌；stylelint 能机器咬死「组件里没有字面样式值」。
- **不适用**：原型、一次性页面 → Tailwind 很快；但 Tailwind 的任意值类（`w-[13px]`）是令牌契约的后门，要主题化的产品慎用。
- **可反悔点**：令牌名稳定，实现可换。

### 全局状态
- **推荐**：**zustand**（轻）。
- **为什么**：API 小，AI 写得稳；和常见渲染引擎有适配。
- **不适用**：状态极复杂、要时间旅行调试 → Redux Toolkit。

### 界面由数据描述（JSON UI / AI 生成界面）
- **情况**：界面要能由 AI 或插件用 JSON 描述、边生成边显示。
- **推荐**：用成熟的 JSON 渲染引擎（如 json-render，Apache-2.0）做**引擎**，**JSON 格式本身归自己**。
- **为什么**：白名单组件、按钮只回传 action、状态绑定、流式渲染都现成；格式归自己，引擎才能换。
- **可反悔点**：格式是契约，引擎是实现。

### 官网 / 营销站
- **推荐**：**Next.js**（Vue 系用 Nuxt）。
- **为什么**：要 SEO、服务端渲染、多语言路由。
- **不适用**：几页静态内容 → 纯静态生成即可。

### 管理后台
- **推荐**：React + 成熟的后台组件库（antd 类）。
- **为什么**：表格、表单、筛选现成，后台不需要品牌化外观。
- **不适用**：后台就是产品门面的一部分（给客户看的控制台）→ 用自己的组件库与设计令牌，别用后台库的默认外观。
- **可反悔点**：后台页面通常最独立，整套换库只影响这一块。

### 多端客户端（手机 / 平板 / 桌面）
- **推荐**：**Tauri 2**。
- **为什么**：一套前端跑五端；壳子轻（Rust，用系统 WebView）；体积远小于 Electron。
- **不适用**：重度依赖 Node 生态的桌面工具 → Electron；需要极致原生体验的手机应用 → 原生或 Flutter / React Native。

### 服务端推送
- **推荐**：**SSE**（Server-Sent Events）。
- **为什么**：标准 HTTP，标准库就能写；浏览器自带重连与 `Last-Event-ID` 断线续传；一个客户端一条事件连接。
- **不适用**：高频双向（协同编辑、游戏）→ WebSocket。

### 状态同步
- **推荐**：真值在服务端；「先 list 再 watch」，每条记录带版本号（epoch / rev / modRev 这一类）。
- **为什么**：断线重连后能知道自己漏了什么；多个客户端看到同一份真值。
- **不适用**：多端要离线编辑同一份数据 → 需要 CRDT 或操作日志，这条推荐不够用。
- **可反悔点**：版本号字段留着，换同步算法时它仍然是断点依据。

### 设备端存储
- **推荐**：数据量小 → **单写者 KV + WAL + 快照**（或嵌入式 KV 库）。
- **为什么**：用不上 SQL；版本号天然就有；比嵌入 SQLite 更小（对轻量形态重要）。
- **不适用**：要复杂查询 / 报表 → SQLite。

### 云端存储
- **推荐**：**PostgreSQL + 对象存储**。
- **为什么**：授权、订单、工单状态机要事务；大文件放对象存储。
- **不适用**：只有键值和缓存、没有事务需求 → 直接用托管 KV，省一套运维。
- **可反悔点**：把表结构与查询收在一层数据访问里，换引擎才不用改业务代码。

### 基础操作系统（做系统 / 设备类产品时）
- **推荐**：满血形态 **Debian 稳定版** + 可回滚文件系统（btrfs 快照）；轻量 / 路由形态 **OpenWrt 稳定版**；图形栈用 Wayland。
- **为什么**：稳定、包多、许可证友好；升级前自动快照，一步回退。
- **不适用**：要跟某个硬件厂商的 BSP 走 → 以厂商支持的发行版为准，别为了统一硬扛。
- **可反悔点**：把平台差异收在 Provider 层（`platform.md`），换底座时只改那一层。

### 本地模型推理
- **推荐**：以 **llama.cpp**（MIT）为内核，自己管理模型；Ollama 只作可选适配器。
- **为什么**：自己能做显存 / 内存预算规划和分档（省内存 / 平衡 / 快），不被上层工具的默认值绑住。
- **不适用**：只是开发机上试模型 → 直接用 Ollama。

### 模型接入
- **推荐**：一层模型网关：多模型按能力路由（图文 / PDF / 音视频 / 推理 / 搜索 / 编程），可设默认、可关，用量可见。
- **为什么**：模型会一直换；网关让上层不关心是哪家。
- **不适用**：只用一个模型、也不打算换 → 网关是多余的一层，直连即可（但把调用收在一个模块里）。
- **可反悔点**：网关的接口就是契约，换模型、加模型都不动上层。

### 插件 / 应用的后端语言
- **推荐**：不限语言：独立进程 + unix socket（或本地 HTTP）；官方 SDK 先出一两种主语言。
- **为什么**：第三方用自己熟的语言；进程隔离就是沙箱边界。
- **不适用**：插件要跑在浏览器沙箱里 → 只能是 JS/WASM，进程隔离那条不成立。
- **可反悔点**：通信走 socket 契约，语言与运行时都能换。

## 全产品约定（一开始就定，几乎零成本；**这一节不是选型卡**）
- 错误码只有一份；时间 UTC + RFC 3339；长操作一律异步、返回任务 id；trace id 贯穿；产品版本用 CalVer，契约与 SDK 用 SemVer。
