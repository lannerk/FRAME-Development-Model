# 开场问题库

> **怎么用**：开新项目时，先看画像里定过哪些，**定过的不问**；剩下的只挑**真正要需求方拍板**的弹窗问（每次 ≤ 4 题，每题 2–4 个选项，推荐放第一并标「（推荐）」，每个选项写代价，不设默认）。
> 技术题能自己定的直接定、写可反悔点，只在正文说一句。**需求方没提到的维度，也要问到**——这正是这份库存在的理由。
>
> 每题四段：**为什么问** · **不问会怎样** · **选项与代价** · **没偏好时推荐**（小白模式下写成「拿不准就选这个」）。
> 标 🔒 的题属于**不可逆**：定了就很难改，务必在写代码前问。

---

## A 产品与范围

**A1 这个东西给谁用、解决什么问题？** 🔒
- 为什么问：一切取舍（端、性能、外观、价格）都从「给谁用」推出来。
- 不问会怎样：做出来的是「开发者自己想要的」，目标用户用不上。
- 选项：先说一句话的用户画像 + 一个最痛的场景。
- 推荐：写成一句「**谁**在**什么场景**下用它**做成什么事**」，放进 `product/vision.md`。

**A2 第一阶段做到哪？终局是什么样？要预留哪些将来的能力？** 🔒
- 为什么问：起步可以小，但终局决定了现在的接口怎么切。
- 不问会怎样：到第二阶段才发现数据结构、权限、协议都要推倒重来。
- 选项：① 第一阶段就是终局（代价：范围大、慢）② 小起步 + 终局写清 + 预留接口（代价：要多想一轮）③ 只管眼前（代价：大概率返工）。
- 推荐：②。

**A3 明确不做什么？**
- 为什么问：边界能挡住需求蔓延。
- 不问会怎样：每个新想法都挤进来，第一阶段永远做不完。
- 推荐：写 3–5 条「不做」，放进 vision。

**A4 叫什么？包名 / 域名 / 命令名要不要先占？** 🔒
- 为什么问：名字进了代码、包名、URL、文档之后，改名成本极高。
- 不问会怎样：上线前才发现撞了系统命令、同行公司或商标。
- 选项：① 先查冲突再定（代价：半天）② 先用代号，发布前再定（代价：发布前要全量替换，且替换容易误伤）。
- 推荐：①；并区分**仓库名 / 包名空间**和**对外品牌**，两者不必相同。

**A5 开源还是闭源？闭源的话哪些面公开？** 🔒
- 为什么问：决定许可证、依赖白名单、仓库结构、公开面门禁。
- 不问会怎样：闭源项目误引入 GPL 依赖；或公开文档里夹带了内部信息。
- 选项：① 闭源 + 文档 / 示例 / AI 目录公开，公开面有自动门禁（代价：要维护门禁）② 全开源（代价：竞争者可直接用，商业模式要另想）③ 全闭源不公开任何东西（代价：生态和 AI 可发现性差）。
- 推荐：视商业模式而定——**这一题必须他拍板**。

**A6 先做通用底座，还是直接做产品？**
- 为什么问：通用底座慢一点，但下一个产品能复用。
- 不问会怎样：两个产品各写一套相同的东西，互相不兼容。
- 选项：① 与产品无关的能力先独立成通用模块（代价：前期慢、要设计契约）② 直接做产品，以后再抽（代价：以后抽取往往等于重写）。
- 推荐：计划做不止一个产品就选 ①。

**A7 怎么赚钱 / 授权怎么做？**
- 为什么问：授权、激活、订阅会影响账号体系和数据模型。
- 不问会怎样：上线后才加授权，要改一大片。
- 选项：一次买断 / 订阅 / 免费 + 增值 / 企业授权；授权形态：签名授权文档（在线 / 离线 / 远程激活）。
- 推荐：**授权（买没买）和权限（准不准）分成两套字段**，无论哪种模式。

## B 端与形态

**B1 有哪些端？** 🔒
- 为什么问：官网、管理后台、设备端、手机 / 桌面客户端、命令行，各自的最优技术不同。
- 不问会怎样：一套技术硬套所有端，某些端体验很差。
- 推荐：**按端选型**（见 `stack.md`）；列出每个端及其第一阶段是否要做。

**B2 有没有「满血版」和「轻量版」两个形态？** 🔒
- 为什么问：两个形态共用到哪一层，决定了代码怎么切。
- 不问会怎样：轻量版变成另一个产品，两套代码两套 bug。
- 选项：① 同一个产品两个形态：共用内核、协议、界面、权限表，平台差异收在一层 Provider 里（代价：要先抽象）② 各做各的（代价：长期双倍维护）。
- 推荐：①；某形态没有某功能用「缺席态」表达，不写平台分叉。

**B3 目标硬件、操作系统、CPU 架构、浏览器下限？**
- 为什么问：决定构建矩阵、测试矩阵和能用的 API。
- 不问会怎样：发布后才发现某类设备跑不起来。
- 推荐：只支持仍有厂商维护的版本；架构优先 amd64 + arm64，不做 32 位，除非用户群明确需要。

**B4 要不要一个用户连多台设备 / 远程访问？**
- 为什么问：多设备会引入账号、寻址、同步、中继。
- 不问会怎样：寻址方式里没有设备 id，以后加多设备要改所有 URL。
- 推荐：哪怕第一阶段只有一台设备，**寻址从第一天就带设备 id**。

## C 技术选型

> 具体推荐与理由见 `stack.md`。这里只列要不要问。

**C1 前端框架：只一个，还是要同时支持几个？** 🔒
- 为什么问：如果做的是组件库 / SDK 给别人用，框架数量决定契约要不要去框架化。
- 推荐：做应用选一个（通常 React）；做给别人用的组件库，考虑多框架同步，契约去框架化。

**C2 后端语言？** 🔒
- 为什么问：影响部署形态、体积、团队与 AI 的熟练度。
- 推荐：设备端 / 单二进制 / 要交叉编译 → Go；以 Web 为主、前后端同语言 → Node + TypeScript（详见 `stack.md`）。

**C3 数据存哪？** 🔒
- 为什么问：数据模型与存储引擎是最难换的东西之一。
- 推荐：设备端数据量小 → 嵌入式存储；云端要事务 → PostgreSQL + 对象存储。

**C4 前后端怎么通信？实时推送用什么？**
- 为什么问：通信方式决定断线重连与断点续传怎么做，而这两件是上线之后最难补的。
- 推荐：普通请求 HTTP + JSON；服务端推送优先 SSE（断线续传自带），真双向高频才用 WebSocket。

**C5 构建与脚手架：用现成的，还是自己做？TS 与 JS 都要吗？**
- 为什么问：如果有下游开发者，脚手架就是产品的一部分。
- 推荐：只自用 → 用官方脚手架；给别人用 → 自己的脚手架（支持非交互参数，方便 AI 调用），TS 与 JS 都支持。

**C6 版本策略？**
- 为什么问：版本策略决定你将来踩到的坑是「已知的」还是「早该修好的」。
- 推荐：一律当天最新稳定版 + 每版一张实测兼容表；实现前读该版本官方文档。

## D 兼容与迁移（常被忘）

**D1 要不要兼容现有的系统 / 数据 / 接口 / 账号？** 🔒
- 为什么问：兼容是最容易被忽略、又最能拖垮排期的约束。
- 不问会怎样：上线时才发现老用户的数据导不进来、老客户端连不上。
- 选项：① 完全兼容（代价：新设计被旧约束绑住）② 提供一次性迁移工具，不长期兼容（代价：迁移窗口要沟通）③ 不兼容，重新开始（代价：老用户流失）。
- 推荐：②；在不可逆清单里写明「对外接口从 v1 开始承诺多久」。

**D2 有没有旧项目可以参考？怎么对待？**
- 为什么问：旧项目里最值钱的是结论和踩过的坑；整段复制代码会把旧约束一起搬过来。
- 推荐：旧项目是资产不是起点——带走结论、设计和踩过的坑（含「否掉了什么」），代码不整段复制。

**D3 对外接口 / 协议 / 文件格式要不要版本号？**
- 为什么问：一旦有第三方依赖，就不能随便改。
- 推荐：所有对外契约从第一天带版本号（如 `name/1`）；「加字段随时可以，删字段不行」。

**D4 要不要兼容第三方生态（导入导出、标准协议）？**
- 为什么问：用行业标准格式，第三方和 AI 才接得上；自造一套要自己写所有适配。
- 推荐：优先用行业标准格式和协议（例如 S3、MQTT、OpenAPI、MCP），而不是自造。

## E 国际化与无障碍（常被忘）

**E1 要不要多语言？** 🔒
- 为什么问：界面文案一旦写死在代码里，后加多语言要过一遍所有页面。
- 不问会怎样：以后接海外客户时，改文案 + 改布局（德语长、阿拉伯语从右到左）一起爆发。
- 选项：① 现在就走 i18n 框架，只出一种语言（代价：每条文案多一个 key，几乎无额外成本）② 现在出多种语言（代价：翻译与校对）③ 不做（代价：以后改动面最大）。
- 推荐：①，**哪怕第一版只有中文**。

**E2 默认语言、要支持哪些语种、要不要从右到左（RTL）？**
- 为什么问：语种与书写方向会影响布局和 CSS 写法，事后改要过一遍所有页面。
- 推荐：默认语言按主要用户定；语种按需加载；CSS 用逻辑属性（`margin-inline-start` 而不是 `margin-left`），RTL 就几乎白送。

**E3 日期、时间、数字、货币、时区怎么处理？**
- 为什么问：时间与数字格式错了是最难发现的一类 bug——只有跨时区、跨地区的用户才会暴露。
- 推荐：存储与传输一律 UTC + RFC 3339；展示时按用户语言环境格式化。

**E4 三件东西分开定：界面文案、给人看的文档、给 AI 的条目，各要几种语言？**
- 为什么问：三类读者对语言的要求不同；混在一起定就会出现「文档全译、AI 条目乱译」。
- 推荐：界面按市场定；文档先源语言 + 英文，其余机翻并标注；**给 AI 的条目一律英文**（模型对英文检索最稳）。

**E5 宿主 / 使用方自己也有 i18n 时怎么整合？**（做组件库、SDK 时问）
- 为什么问：使用方已经有一套 i18n 时，**两套语言源一定不同步**。
- 推荐：一个语言源，桥接主流 i18n 库，不让使用方维护两套。

**E6 无障碍（键盘、读屏、高对比）做到什么程度？**
- 为什么问：做到什么程度决定要不要多一套外观，也决定政府 / 企业采购过不过。
- 选项：① 默认外观就达标（代价：设计自由度受限）② 默认外观守设计标准，另有高对比外观承担无障碍（代价：多一套外观要测）③ 暂不做（代价：部分用户与政府 / 企业采购会被挡）。
- 推荐：至少用成熟的无头组件层（焦点、键盘、ARIA 不自己写），再在 ① ② 之间拍板。

## F 体验与外观

**F1 外观要不要可换（主题 / 风格包）？**
- 为什么问：可换就必须从第一天把样式抽成设计令牌。
- 不问会怎样：颜色字号散落在几百个组件里，后加主题要全改。
- 推荐：不论要不要换，**组件里只许用令牌（`var(--*)`），不许出现字面样式值**——这条几乎零成本，后悔成本极高。

**F2 浅色 / 深色 / 高对比 / 透明度，要哪些？**
- 为什么问：外观维度不正交，组合数会爆炸，每加一种都要改每个组件。
- 推荐：至少浅 + 深；外观维度彼此正交（风格 × 外观 × 密度 × 动效 × 方向）。

**F3 布局有几套（桌面 / 单窗口 / 手机）？**
- 为什么问：布局套数决定模块能不能只声明语义；位置写死了，以后换布局要改每个模块。
- 推荐：布局与风格分开，模块只声明语义，布局决定放哪。

**F4 图标、logo、字体从哪来？**
- 为什么问：素材来源牵着许可证和品牌一致性；事后替换要过所有页面与包。
- 推荐：用需求方已有的资产，先问「现在正在用的是哪一个」；字体检查许可证（OFL 可用）。

## G 数据、安全与权限

**G1 用户数据放哪？经不经过我们的服务器？** 🔒
- 为什么问：数据经不经过你，同时决定隐私承诺、成本与合规；事后改是改架构。
- 推荐：控制面（账号、授权、寻址）我们做，数据面尽量不经过我们；兜底中继限流并在界面上明说。

**G2 机密（密码、令牌、API key）怎么存？**
- 为什么问：机密泄露几乎都是从日志和诊断包里漏出去的；事后补要审所有输出面。
- 推荐：加密的机密键；不进环境变量、日志、诊断包、提示词；schema 标 `secret` 自动打码。

**G3 权限模型：有几种角色？要不要审计？** 🔒
- 为什么问：审计与角色事后加，等于把权限判断塞进已经写好的每个入口。
- 推荐：从第一天有「谁在什么时候做了什么」的审计；多用户就要角色。

**G4 升级、安装、配置变更能不能回退？**
- 为什么问：能不能回退决定人敢不敢升级；事后补要给每个有状态的步骤加快照。
- 推荐：都能一步回退；有状态的升级前自动快照。

**G5 错误收集要不要？默认开还是用户选？**
- 为什么问：默认开还是用户选，是隐私与可维护性的取舍；上线后再改要重新征求同意。
- 选项：① 让用户选是否上报（代价：数据少）② 默认上报可关（代价：隐私争议）③ 不收集（代价：线上问题难查）。
- 推荐：①，并让收集到的缺陷能直接回流到开发队列。

## H AI

**H1 这个产品的使用者里有 AI 吗？** 🔒
- 为什么问：有 AI 使用者，就要给它能直接调用的接口、按需检索的说明、诊断码。
- 推荐：默认按「有」设计——成本不高，收益越来越大。

**H2 给 AI 的调用面要哪几种（JSON / CLI / MCP / skill）？**
- 为什么问：调用面缺一种，AI 就会在那一段变成「人能做、它不能做」。
- 推荐：一份动作定义同源生成 HTTP / CLI / MCP / 界面按钮；说明按「总览 → 索引 → 条目」分层检索、带版本号，不一次灌进上下文。

**H3 产品里有没有 AI 功能？关掉 AI 还能用吗？**
- 为什么问：这一题决定 AI 是增强还是依赖，也决定断网时产品还剩多少。
- 推荐：关掉 AI 仍完整可用；AI 功能做成可替换的模块，模型可配置。

**H4 AI 能做多大的事？**（有 AI 操作者时问） 🔒
- 为什么问：这是权限边界；事后收窄会打断已经跑起来的流程。
- 推荐：AI 有独立身份，不默认继承人的全部权限；三档——**读给它 · 写要问 · 危险只能提议**，人批准后执行，审计记「由 AI 发起」。

**H5 模型本地跑还是用云？**
- 为什么问：本地还是云，决定硬件预算、隐私承诺和断网时的表现。
- 选项：① 云模型（代价：费用、隐私、断网不可用）② 本地模型（代价：硬件要求）③ 两者都支持、按能力路由（代价：多一层网关）。
- 推荐：③，并让用户看得到用量。

**H6 要不要 AI 评测进验收？**
- 为什么问：没有评测集，AI 相关改动只能靠「感觉变好了」，既证明不了也没法判断该不该回退。
- 推荐：要——AI 相关功能用固定评测集验收，否则「感觉变好了」无法证明。

## I 扩展性

**I1 要不要第三方插件 / 应用？** 🔒
- 为什么问：要的话，内置功能也得按公开协议写。
- 不问会怎样：以后开放时发现内置功能全是后门调用，第三方做不到。
- 推荐：哪怕第一阶段不开放，**内置也按公开协议写**；协议分 core + profile，将来别的产品只扩展字段。

**I2 生态分几步开？**
- 为什么问：开放的顺序就是风险的顺序；一步开到底，审核与兼容问题会一起爆发。
- 推荐：内置按协议 → 第一个可安装模块 → 无代码的纯资源包（主题、语言、技能）对第三方开放 → 带后端的第三方（签名、审核）→ 付费。

## J 文档、测试与交付

**J1 文档给谁看？要哪几种？**
- 为什么问：给人看的和给 AI 看的要求不同，混成一份会两边都不好用。
- 推荐：给人看的（指南 + 每个组件 / 接口一页 + 总览页 + 在线案例）与给 AI 看的分开；都由契约生成，大版本并存。

**J2 测试做到什么程度？谁验收？**
- 为什么问：谁验收决定「做完了」由谁说；自己审自己等于没有验收。
- 推荐：每条规矩能机器验（带反向断言）；验收由独立的一席做，不自己审自己。

**J3 发布渠道与 CI？**
- 为什么问：渠道牵涉账号、费用与审核周期；临上线才定会卡住发布。
- 选项：公共包仓库 / 私有源 / 应用商店 / 镜像；CI 平台。
- 推荐：**这一题通常要他拍板**（涉及账号与费用）。

**J4 开发节奏：一个个做完整，还是先铺骨架？**
- 为什么问：节奏决定架构问题什么时候暴露；先做简单的，难题会留到最后才炸。
- 推荐：先做一个简单样板，再**先做最难的**验证架构；每条任务有完成清单，清单加步骤时回补旧的。

## K 许可证与依赖

**K1 依赖许可证白名单？** 🔒
- 为什么问：许可证问题发现得越晚越贵，可能要整段替换依赖。
- 推荐：MIT / Apache-2.0 / BSD / ISC / OFL 直接用；MPL 不改其文件可用；LGPL 只动态链接；GPL / AGPL 不链接进闭源；无许可证不用；不 fork、不 vendor。

**K2 第三方是内嵌还是 peer 依赖？**
- 为什么问：内嵌还是 peer，决定升级第三方时责任在谁，也决定体积与版本冲突。
- 推荐：适配器模式，第三方做 peer 依赖，用户自己装、自己升级。

## L 对外材料

**L1 给谁看（投资人 / 客户 / 开发者）？要哪几种格式？**
- 为什么问：不同读者要的格式不同；一份母本同源出，三份材料才不会互相矛盾。
- 推荐：一份 Markdown 母本，同源出网页 / PPT / PDF；PDF 逐页排版，不是网页打印。

**L2 写什么、不写什么？**
- 为什么问：材料里一句站不住的话会让整份失信，所以边界要先定。
- 推荐：写能力、生态、想象空间；**不写「什么还没做」和内部版本区别**；不放无来源的市场数字（要数字另出一份带口径）。

**L3 视觉用什么？**
- 为什么问：视觉素材牵着许可证与品牌一致；事后换要重出所有格式。
- 推荐：用正在用的 logo 与图标；网页自带 `<!doctype>` 与 `<meta charset="utf-8">`；面向国内访问不引境外字体服务。
