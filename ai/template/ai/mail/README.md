# 席间信箱 —— 怎么发、怎么读、什么不该进

> **这一份按需读**（要发信、或不确定该不该发的时候读），**不进开场必读**。
> 开场必读的是你自己那一份 `ai/mail/to-<你这一席>.md`。守门：`bash ops/verify/check-mail.sh`。

## 它和别的台账不是一回事（**最容易搞混的地方**）

| 要传的是 | 进哪 | 不要进信箱的理由 |
|---|---|---|
| 需求方说的话（需求 / bug / 临时决定） | **收件簿** `product/requirements/inbox.md` | 那是他的话，有清零守门 |
| **开发席 ↔ 审查席之间关于任务与 bug 的一切来往**：派活 · 方案 · 开发回报 · 自测 · 审查结论 · 复测 · 返工 · 遗留 · 阻塞 · 要条件 | **任务** `ai/tasks/T-####` / **bug** `ai/bugs/B-####` | 🔴 **这两席之间绝大多数话都不走信箱。** 台账才是活的真相；**写进信箱就等于把开发追踪信息从台账里抽走**（需求方 2026-09-15 原话：「否则就会丢失开发追踪信息」）。守门会把这两席之间**提到 `T-####`／`B-####` 的信直接报红** |
| bug 本身（现象 / 复现 / 定位 / 修复 / 复测） | **`ai/bugs/B-####`** | 同上 |
| 「以后都这么办」的项目常识 | **项目记忆** `ai/memory.md` | 记忆是给所有人长期用的，不是给某一席的一次性留言 |
| 「这条规矩要改」的最终落地 | **维护记录** `ai/rules/maintenance-log.md` | 那是改完之后的账；**改之前的建议才走信箱** |
| **跨席的建议 / 转告 / 通知 / 请求 / 答复** | **信箱** `ai/mail/to-<收信席>/from-<发信席>.md` | 就是它 |

### 🔴 开发席 ↔ 审查席：**基本上不需要互相发信**

需求方 2026-09-15 原话：「**审查和开发两者基本上无互相发信的需要，场景很少**」；
「**下达开发需求、反馈 bug、开发做需求、修 bug、反馈，都是通过项目原本的约定方式协同工作**」。
**默认答案是「不发」。** 一条任务从派活到关闭，全程写在 `ai/tasks/T-####`（和它关联的 `ai/bugs/B-####`）里——
**那是开发追踪的唯一现场**，谁接手都能顺着它看完整条线。信箱只放**跟具体任务无关**的话，比如：

| 能发 | 不能发（走台账） |
|---|---|
| 「我这一席够不到真机终端，你的只读探测能不能帮我取一份栈」这类**能力／通道**问题 | 「T-0031 我改完了」「B-0001 复测过了」 |
| 「以后这类前端 bug 我都能在容器里复现，别再等真机」这类**做法约定**（顺手也该进 `ai/memory.md`） | 「这条方案我不同意，理由是……」（写任务里的「怎么做（建议·可反驳）」） |
| 规矩层面的建议（**但那是发给维护席的**） | 「还有什么要做 / 还有什么 bug」（审查席按范围从台账里捞给需求方） |

**判据一句话**：**这句话属于某一条 `T-####`／`B-####` 吗？属于就写进那个文件，不要发信。**

守门对这一对另加两条：**类型只许「请求」或「通知」**（建议/转告/答复都说明在谈任务）、**未处置最多 1 封**（第 2 封就说明在拿信箱当开发通道）。

🔴 **信箱不是派活的地方。** 一封信如果只写了个 `T-####` / `B-####` 让对方去干，
那件事本来就该在台账里——守门会报红。**信箱传的是「话」，台账传的是「活」。**

## 一封信长什么样

信箱是 **`ai/mail/to-<收信席>/from-<发信席>.md`**，四席各三份投递口（共 12 份）：**一个发信人一份，谁都不碰别人的文件，所以不会有 git 冲突**（需求方 2026-09-15：归档要一席一份；同理，投递口拆到发信人这一层才算拆干净）。**发信人已经写在文件名里，所以信里不再有「谁发的」那一栏**——同一个事实不双写。

**一行就是一封信**，五栏一个都不许空（没有就写 `—`）：

| 栏 | 怎么填 |
|---|---|
| 日期 | `YYYY-MM-DD`，发信那天 |
| 要我做什么 | **一句话，动词开头**，让收信人看完就知道要干什么。**不许只填一个编号** |
| 细节在哪 | 路径，可多份；正文**超过三行就写成文件**，信里只留路径（文件放 `claude-outputs/<发信席>/<日期>-<题>.md`）。真的三行说得完就写 `—` |
| 类型 | 建议 / 转告 / 通知 / 请求 / 答复 |
| 要不要回 | 要 / 不要 |

**每份投递口上限 12 行**（约 6 封）；满了不是加大上限，是**没人读或者发信太碎**。**一封信躺过 7 天没处置守门报红**：要么处置，要么发信人收回改走别的路。

**发信四条**（和 `ai/rules/requester.md`「要转告另一席」同一套判据）：

1. **自成一体**——收信那一席不看原报告也能照着做，要细节再去路径里找。
2. **一封信只讲一件事**——否则没法单独处置、单独归档。
3. 每条 = **现象 + 证据（命令／输出／行号）+ 拟改法 + 代价**。
4. **发信不等于对方做了**——送到不是做完。**发完还要在会话里报一句**（需求方 2026-09-15：「A 发信给 B，A 也需要在 session 汇报发信信息」）：**发给谁 · 一句话说了什么 · 细节文件在哪**；他看到这句就知道这件事已经交出去了，**不用他再转达**。

> **发收信与归档的大概逻辑**（需求方 2026-09-15 定的）：A 在 `to-B/from-A.md` 加一行 → **A 在会话里报「已发信给 B：……」** → B 下次开场（或需求方说 `查信`）读到 → **B 在会话里报收信小结** → B 处置 → **B 把那一行移进自己的 `archive/B-<年月>.md`**（归档归收信人，**信发给谁就属于谁**）。

**群发**：发信人**往另外三席的 `from-<自己>.md` 各写一行**，各自读、各自处置。（不搞「最后一个已读的人删除」——只要有人漏读就永远删不掉，还看不出卡在谁那儿。）

## 🔴 一来一回就到顶（防对聊死循环）

需求方 2026-09-15 提醒：**「这个需要有边界，否则可能会造成死循环，不断给对方回信」**。所以：

**只有一种情况要回信：看了信之后冒出新的问题，而你自己定不了、必须再问一次。**
（需求方 2026-09-15 原话：「对信的内容有新的问题不能解决需要再次咨询」才回；
「有问题已经拍板解决或者自行决定，那就不需要再回信」；「像重载规范这种通知型的信息，也不需要回信」。）

| 处置完的情形 | 要不要回 |
|---|---|
| 照做了 / 自己拍了板 / 转成了任务 | **不回**——**归档那一行就是回执**，发信人去 `archive/` 查得到 |
| 通知型（规矩改了要重载、模板同步了、机器换地址了） | **不回** |
| 拒收 | **回一封「答复」写明理由**，仅此一封 |
| 看完冒出新问题、自己定不了 | **回一封「请求」**，把问题问清楚 |

- **「答复」和「通知」自己的「要不要回」只能是「不要」**——守门会报红。
- **还谈不完，就换轨**：要动手的开 `T-####`／`B-####`，要判断的开**顾问咨询单派给监督席**
  （`ai/rules/workflow.md` §五之二）。**信箱不是聊天室**，它只负责把一件事交到对方手上。
- **不许为「你没说服我」再来一轮**。还僵着＝这件事要需求方拍板，写进他的收件簿，别在信箱里耗。
- **不许发客套回执**（「收到」「已处理，谢谢」）——那是纯烧 token 的死循环起点。

## 🔴 发信之前先看对方信箱（不许刷屏）

需求方 2026-09-15：「发信人给同一个角色发送多个信息或相同信息未读，**有阻止发信的机制**」。所以发信前**先读一眼 `to-<对方>/from-<自己>.md`**（只需要看你自己那一份）：

| 看到 | 怎么办 |
|---|---|
| 同一件事你已经发过、对方还没处置 | **改那封信**（或改它指向的细节文件），**不许再发一封**。守门会把重复的信报红 |
| 你给对方的未处置信已经有 3 封（非通知类，就在你自己那一份里） | **停手**。这不是他手慢，是**你把信箱当工单系统了**——该开任务或顾问咨询单 |
| 你那一份已经 15 行 | 同上，**先等他清，或者直接换轨** |

**通知型（如「重载规范」）也不许重复发**：改了三轮就改那一封的日期和内容，**收信人只会执行一次**。

## 怎么读、怎么处置

**开场第一件事**就是读自己那一个目录 `ai/mail/to-<我这一席>/`（三份，一个发信人一份）。口令 `查信` 也是这件事。读法是**三步，不是逐封反应**
（需求方 2026-09-15：「角色读信的机制是一次过全读，自己总结去重，是否需要处理等等」）：

0. **先把读到的信抄进自己的 `archive/<我这一席>-<年月>.md`**（处置结果先写「在办」），**再动手**——
   信是别席写的活文件，**随时会被收回或重写**；2026-09-15 真发生过：处置完回头归档，原件已经没了，而它从没进过 git。
1. **一次过全读**——**三份一起读进来**（`cat ai/mail/to-<我这一席>/from-*.md` 最省事），别读一封就动手。
2. **自己总结去重**：**同一件事只做一次**。维护席连改三轮规范、发了三条「重载规范」，
   你**只重载一次**，剩下的一并归档，归档那行写 `照做：与上一条重复，合并处理`。
3. **再按从旧到新逐条处置**——顺序只影响处置顺序，不影响第 1、2 步。
4. **在会话里报一张小结**（需求方 2026-09-15：「知道如何处理的时候，也在 session 内显示出来」）：
   **收到几封 → 去重后是几件 → 每件怎么处置**。样子照这个来：

```
查信：3 封（来自 监督席 ×2、审查席 ×1），去重后 2 件
1. 监督席 · 规范三条建议（claude-outputs/supervisor/<日期>-体检.md）→ 照做，这一轮改完
2. 审查席 · 请我出回写步骤单 → 转成 T-0036
（第 3 封与第 1 封同事，合并处理）
无需回信：都不是「有新问题定不了」的那种
```

🔴 **收信异常要上报，不要自己扛**：同一发信人**非通知类堆过 3 封**没处置（守门会报红），
或者反复收到同一件事，**查信后告诉需求方和发信人**：「别再往这儿发，这件事该开任务或咨询单」。
处置只有三种，**做完把那一行从信箱移进 `ai/mail/archive/<我这一席>-<年月>.md`**（追加一行，带处置结果）——
🔴 **归档归收信人**：维护席发给监督席的信，**监督席**处置完归进 `supervisor-<年月>.md`——**信发给谁就属于谁**，发信人不归档（要查自己发出去的信，去对方那一份里找）。归档表头：`| 日期 | 谁发的 | 要做什么 | 细节在哪 | 处置结果 |`。
**归档每席一份，不是共用一份**：共用一份等于四席往同一个文件尾巴上追加，**git 冲突是必然的**（需求方 2026-09-15 指出）：

| 处置 | 什么时候 | 归档那行写什么 |
|---|---|---|
| **照做** | 这一轮就能做掉 | `照做：<做了什么>` |
| **转成活** | 是一件要排期的事 | `转成 T-#### / B-####` |
| **拒收** | 不该我做、或不同意 | `拒收：<理由>`，并**回一封「答复」**给发信人 |

🔴 **迁移／改名／删除信箱或归档文件前先 `wc -l` 看有没有数据行**，有就**先搬内容再删壳**——**判文件里有什么，不判文件名长什么样**（2026-09-15 真事：按名字判成「空壳」删掉，把监督席写好处置结果的两行归档一起删了，靠 `git show HEAD:` 捞回；守门已补「归档只许增不许减」）。
🔴 **别席的活文件只许追加，不许整份重写**（同一天又用整份重写「恢复」那份归档，把它刚写的一版盖掉，未提交连 git 都没有）。**要加行就追加，要改别人的行先跟他说。**

🔴 **不许在原处标「已读」。** 信箱只放未读——**已读堆在里面，下一个人就不会认真看了**
（收件簿当年就是这么烂掉的）。归档是为了将来能回答「这封信到底有没有人管、怎么处理的」。


## 一个必须知道的边界

信箱只在那一席**下一次开场**、或需求方说 `查信` / `重载规范` 时被读到。
**正在跑的会话不会自己醒。** 所以「规矩改了」这类通知，除了发信，
还要请需求方对在跑的会话说一句 `重载规范`（它现在顺带查信）。
