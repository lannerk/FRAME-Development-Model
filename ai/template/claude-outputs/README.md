# claude-outputs/ —— Claude 的草稿区

这里放 **Claude 干活过程中产出的一切**：截图、实测输出、原型、一次性报告、给需求方看的稿子、调研笔记。

**为什么单独一个目录**：这些东西在对话里要能随手引用（「你看 `claude-outputs/shared/screenshot/xxx.png`」），
但它们**不是项目的正式文件**——正式文件有固定的家、有生命周期、有人维护。
草稿放进正式目录会把正式目录冲乱；草稿散在对话里又找不回来。所以给它一个自己的地方。

## 放哪

| 子目录 | 放什么 |
|---|---|
| `developer/` | 自检清单的原始输出、实测数据、交付说明、构建日志 |
| `reviewer/` | 审查记录、派工单、真机反馈整理、对监督产出的核实记录 |
| `supervisor/` | 监督者的报告、方案、专题研究 —— **原样入库，任何人不改一个字** |
| `maintainer/` | 维护者的验收题面与评分表、规范变更说明 —— 它的**维护记录**不在这儿，在 `ai/rules/maintenance-log.md` |
| `shared/prototype/` | 可交互原型 html、渲染出来的效果图 |
| `shared/screenshot/` | 真机截图、界面对比图 |
| `shared/measurement/` | 实测数字、扫描清单、对账结果 |

**命名一律 `<日期>-<一句话>.<扩展名>`**，日期在前便于排序，例：`2026-09-16-VPN六态渲染.png`。

## ★ 转正表 —— 需求方说「这个采纳」之后，搬到哪

**采纳 ＝ 它从此有人维护、会被引用、要跟着实现更新。** 那就必须搬出草稿区。
搬的时候三件事一起做：**移文件 → 补文件头 → 在对应索引里登记一行**。

| 草稿区里是什么 | 采纳后搬到 | 还要做什么 |
|---|---|---|
| **技术方案 / 实施方案** | **`ai/specs/<名>.md`** | 见下面「§ 技术方案转正」 |
| **调研报告**（选型比较、上游能力调研） | 结论并进对应的 `ai/specs/<名>.md`；原报告留在草稿区 | 在方案的「依据」里指回原报告的路径 |
| **需求方的原话整理稿** | `product/requirements/verbatim/<日期>-<话题>.md` | **一字不改**；同时由审查者整理出 `product/requirements/specs/<功能>.md` |
| **可验收规格** | `product/requirements/specs/<功能>.md` | 在 `ai/decisions/` 记一条 AD，标明「需求方拍板」 |
| **正式需求条目 R-xx** | `product/requirements/formal/` | 更新 `docs/features.md` 的功能清单与状态 |
| **功能的原型 / 设计稿 / 图标**（审查者在草稿区自己命名的那个目录，整个搬） | **`product/design/prototype/_PROJECT_/feature/<同名目录>/`** | 见下面「§ 设计稿转正」 |
| **整套原型**（= 运行态镜像，如桌面、安装器） | `product/design/prototype/_PROJECT_/suite/<套>/` | 改完跑原型自检；`src/<project>/web/` 与它互为镜像的部分要同步 |
| **确认后的 UI 基线资产**（图标 SVG、配色、标注图） | `product/design/ui/` | 令牌进项目的令牌文件，并让它在样式总览页看得到 |
| **参考设计 / 竞品截图** | `product/design/reference/` | 无 |
| **要长期生效的规矩**（新的工程约定） | `ai/rules/conventions.md` 加一条 | 同时记一条 AD 说明它是哪次事故来的 |
| **架构说明 / 目录说明 / 运维手册的修订** | `docs/` 对应那一份 | 跑 `ai/check-links.sh`，断链必须为 0 |
| **系统架构设计** | `ai/specs/architecture.md`（`docs/architecture.md` 只留导读） | 改动一律**另记一条 AD**——它是别人做决定的地基 |
| **数据库设计** | `ai/specs/database.md`；ER 图等图片 `product/design/database/` | 同上；迁移策略也写在里面 |
| **技术选型** | `ai/specs/tech-stack.md` | 写清**版本**、为什么选它、**被否掉的是什么**；同上要记 AD |
| **开发计划 / 里程碑** | `product/plan/roadmap.md` + `product/plan/milestones/M-##-<名>.md` | 里程碑列 `T-####`，任务写 `关联里程碑:`，两边互指 |
| **脚本**（自检、审计、构建） | 跟源码走的进 `src/<project>/tools/`；部署运维的进 `ops/scripts/` | 进开发者自检清单的，要在 `ai/rules/conventions.md` §五登记 |
| **一次性排查报告 / 根因分析** | **不搬**，留在草稿区 | 结论写进相关任务的「审查结论」或 `ai/state/now.md` 的「别再踩的」 |
| **真机截图 / 实测输出 / 自检日志** | **不搬**，留在草稿区 | 它们是证据，由任务文件按路径引用 |

## § 设计稿转正（需求方确认之后）

**草稿阶段**：审查者在 `claude-outputs/reviewer/<自己命名>/` 里做——图标、图片、html 原型、说明，随便改，不用登记。

**需求方确认之后**，整个目录搬到：

```
product/design/prototype/_PROJECT_/feature/<同名目录>/
                         ↑           ↑         ↑
                  源码子目录名   固定一层    草稿区那个名字，不改
```

例：`claude-outputs/reviewer/VPN/` → `product/design/prototype/_PROJECT_/feature/VPN/`

搬的时候三件事一起做：

1. **整个目录搬过去，名字不改**——名字是它和草稿、和任务之间的唯一线索。
2. **补一份 `README.md`**：状态、定稿日期、关联决策、里面有什么、**开发该怎么用**（原型照它做 / 图标直接取用不要自己画 / 说明里的边界与验收点）。
3. **在用到它的任务文件里填 `关联原型:`**，指向这个正式路径。

**搬完之后**：正式目录那一份是**唯一权威**；草稿区那份不再更新，**也不许再被任何正式文件引用**。
要改设计，改正式目录那一份（它会跟着实现更新），不是回草稿区改。

> **开发者只认 `product/design/` 下的路径。** 任务文件里如果出现 `claude-outputs/` 的设计稿路径，
> 说明这条任务开早了——设计还没定稿，回去找审查者。

## § 技术方案转正（确认或更新之后）

**草稿阶段**：审查者在 `claude-outputs/reviewer/` 里写，怎么改都行。

**审查者与需求方确认之后**，搬到 **`ai/specs/<名>.md`**，并且：

1. 补文件头（状态 `已定` / 版本 / 最后更新 / 关联决策 / 引用它的任务）；
2. 在 `ai/specs/index.md` 的「在用」表里登记一行；
3. 任务文件里填 `关联方案:` 指向它。

**以后的更新都在 `ai/specs/` 里改**，不回草稿区：bump 版本 + 写一行变更记录 + 到引用它的未结任务里各留一行提醒。
**方案一旦定案就是「开工必读」**，实现和它不一致时**改方案**，不要让它停在提案那天。

---

**判断搬不搬只问一句：以后还会有人来改它吗？**
会 → 搬到正式目录，它需要一个维护者和一个索引。
不会 → 留在草稿区，它是这一刻的证据，越原样越好。

## 清理

草稿区**会一直长**（旧结构里它到过 55MB / 83 个文件）。规矩两条：

1. **每季度（或每 10 段）整理一次**：把不再被任何任务文件引用的，整批移进 `archive/claude-outputs/<年季>/`。
2. **不删**——它们在 git 里也有，但留着比翻 git 快。移走只是让当前目录还看得清。

## 三条不许

- **不许把草稿区当正式目录引用**：`ai/specs/` 和 `docs/` 里的正式文件，不许把草稿区的路径写成「依据」以外的用途。
- **不许改 `supervisor/` 里的任何文件**——要纠正，由审查者在 `reviewer/` 另写核实记录。
- **不许在这里放二进制产物**（可执行文件、安装包、镜像）——那些进 `dist/`，不入库。

## 审查席的六类设计产物，各自的家

> 从 `ai/roles/reviewer.md` §二之二 搬来的全文。手册里只留一张表和一句指针。

审查席不只是「审别人做得对不对」，**系统长什么样也是你定的**：

| 你的活 | 定稿产物放哪 | 谁拍板 |
|---|---|---|
| **系统架构设计** | `ai/specs/architecture.md`（唯一真相）；`docs/architecture.md` 只留一页导读指过来 | 需求方 |
| **数据库设计** | `ai/specs/database.md`（表、字段、索引、迁移策略）；ER 图等图片放 `product/design/database/` | 需求方 |
| **UI 设计** | 规范与基线资产 `product/design/ui/`；具体功能的原型与图标 `product/design/prototype/_PROJECT_/feature/<名>/` | 需求方 |
| **技术选型** | `ai/specs/tech-stack.md`（选了什么、**版本**、为什么、被否掉的是什么）；**每次选型另记一条 AD** | 需求方 |
| **原始需求梳理拆分** | 原话 `product/requirements/verbatim/` → 可验收规格 `product/requirements/specs/<功能>.md` → 任务 `ai/tasks/` | 需求方 |
| **大需求的开发计划** | `product/plan/roadmap.md` + `product/plan/milestones/M-##-<名>.md` | 需求方 |

**三条通用规矩**：

1. **一律先草稿后转正**：都在 `claude-outputs/reviewer/<自己命名>/` 里做，**需求方确认之后**才搬到上面那一列，
   并在对应的 `index.md` 登记一行。转正之后**只改正式那一份**（`claude-outputs/README.md`）。
2. **架构 / 数据库 / 技术选型这三样，改动一律带一条 AD。** 它们是别人做决定时的地基，
   **地基换了没人通知，塌的是上面所有东西**。
3. **判据永远是「用户眼里是不是同一件事」，不是「改动大不大」**——是同一件事就**更新那一份**，
   不许开 `-v2`。（和设计稿、技术方案同一条规矩。）

### 什么时候要做计划

一个需求**一条任务装不下**——要分批、要排先后、要跨多个功能——就**先出计划再开任务**。
小改直接开任务，**不要为了走流程造计划**。计划怎么写见 `product/plan/README.md`。

### 源码目录结构：**跟语言走，不跟这套模板走**

`src/<project>/` 底下**按那门语言/框架自己的官方约定组织**——
Go 就 `cmd/` `internal/` `pkg/`，Java/Maven 就 `src/main/java`，Python 就包目录 + `pyproject.toml`，
前端框架就按它脚手架生成的那套。

- **不要把别的语言的习惯套上去**，也不要为了「看起来整齐」自己发明一套。
  违背语言约定的代价是：**它自带的工具链全部失灵**（构建、测试发现、打包、IDE 索引），
  而且每个新来的人都要先学你这一套。
- **本项目用的是哪套约定，写进 `ai/specs/tech-stack.md`**，并在 `docs/repo-layout.md` 提一句。
- 这套模板管的是 `src/` **外面**那些（`ai/` `product/` `docs/` `ops/`），**里面归语言管**。

## 出设计 / 出方案：先草稿，确认后转正（从 `reviewer.md` §四搬来）

- **草稿阶段**在 `claude-outputs/reviewer/<自己命名>/` 里做（图标、原型 html、说明），随便改，不用登记。
- **需求方确认之后**按 `claude-outputs/README.md` 的两条转正规矩搬：
  - 设计稿 → `product/design/prototype/_PROJECT_/feature/<同名目录>/`，补 README，任务里填 `关联原型:`，
    并在 `feature/index.md` 登记一行
  - **搬之前先和需求方确认：这是新 feature，还是更新已有的？** 判据是「用户眼里是不是同一个功能」，
    不是改动大小。是更新就**直接改那个目录 + 加一行变更记录**，**不许开 `xxx-v2/`**
  - 技术方案 → `ai/specs/<名>.md`，补文件头，`specs/index.md` 登记，任务里填 `关联方案:`
- **转正之后草稿区那份就不动了**。以后要改设计或改方案，**改正式目录那一份**——
  两处都在改，开发就不知道该信哪份。

## 复盘材料不由被审的那一席自己总结（从 `workflow.md` §五搬来）

需求方要复盘时：**审查席交的是原始材料**——原话逐字 + 时间线，**不做评价**，
**放 `claude-outputs/reviewer/` 入库**（**不许放 `tmp/`**：`tmp/` 不入库、每段清空，
而 `ai/rules/layout.md` §六 明写「不许从 `tmp/` 引用任何东西」）。
**评价由监督席出**，走 §五之二 的咨询单。

**为什么**：自评是**站在席位里**写的。真事——审查席那份九条自评很诚恳，
但监督席另外抓到的六条它**一条都没列**，而那六条恰好都需要**跳出席位**才看得见
（把绕法当交付 / 源码里查得到的当成要真机 / 用半个机制否定需求方的观察 / 台账滞后 / 证据放 `tmp/`）。
**自评在结构上看不见这一类。**
