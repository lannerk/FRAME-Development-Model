# Generic product principles

> Judgements that hold across projects. Each one says **what to do** and **why**. Where the profile settles it differently, the profile wins.

| Principle | What to do | Why |
|---|---|---|
| **Start small, settle the endgame first** | Phase one may be tiny, but write the endgame down; capabilities you will want later get **their interface reserved now** (registered, not implemented) | "We only discovered it at that point, so we rebuilt it" is the most expensive rework there is |
| **Settle the irreversible list first** | Before the first line of code, list every decision that means a full rebuild if changed, and get each ruled on; the rest can move fast | There are only a few irreversible decisions, but one wrong one topples the build; reversible ones are not worth a meeting |
| **Match the industry standard** | Do it the way the field already does it (package format, plugin model, component library, docs site), then look for a better way | Users and AI already know the standard way; inventing your own charges everyone a learning fee |
| **Make the generic base standalone first** | Capabilities unrelated to the product (component library, rule engine, plugin protocol, state sync …) become generic modules first, then the product pulls them in | The next product reuses them directly; a generic module's boundary forces you to think the contract through |
| **Contract plus adapters** | One contract per capability: **your own implementation plus adapters for the mainstream third parties**, interchangeable; cut the abstraction along **capability**, never along vendor | Users can swap implementations; a third party's upgrade or death does not sink you |
| **Pick a stack per surface** | Marketing site, admin console, device side, client apps and the CLI each get their own | "One stack for everything" leaves some surface crippled (a marketing site with no SEO, for instance) |
| **AI first** | Treat AI as one of the primary users: interfaces it can call directly, docs it can retrieve on demand, diagnostic codes, self-check commands | Building and using are increasingly done by AI; if AI cannot use it well, the product is not usable well |
| **AI-native, but AI is not required** | With AI turned off it is still a complete product; with AI on it is not one more chat box but **one more operator with an identity, permissions, an audit trail and a sandbox** | A product that dies without AI is unreliable; a product where AI can do anything is unsafe |
| **Generate from one source, never by hand** | Docs, API tables, capability matrices and AI entries are generated from the contracts and the tests | Anything handwritten drifts from the code |
| **Install only what was chosen** | The user installs the frameworks, implementations, languages and optional capabilities he picked | Size and dependency conflicts both come from "install everything" |
| **Versions and a compatibility table** | Third parties and runtimes always at the day's latest stable; every release ships a compatibility table with the **exact versions tested**; widen the range only after testing the new one | "Should be compatible" is not compatible; the cost of old versions compounds |
| **Read that version's own docs before implementing** | Read the official docs or source of the version you are on, never from memory | APIs change between majors, and writing from memory is the main source of bugs |
| **Built-in and third party share one path** | Built-in features go through the public protocol too, just with more capabilities available; there is no insider back door | A back door means third parties can never match the built-ins, and no ecosystem forms |
| **Declare semantics, let the system decide presentation** | A module declares "this is a toggle, the icon is wifi, it needs a window"; how it looks belongs to the style, where it goes belongs to the layout | Swapping style, layout or surface then touches no module |
| **A feature may be absent; the path may not fork** | A form factor lacking a feature is a legal state that the layers above handle as "absent"; **never write `if platform == X`** | A fork gets copied at every call site and becomes unmaintainable |
| **Everything can be rolled back** | Upgrades, installs, a rule taking effect, every self-improvement by an AI — each is one step from being undone | Being willing to change things depends on being able to undo them |
| **Data does not pass through us** | We run the control plane (accounts, licensing, addressing); user data goes direct where possible, with a rate-limited fallback relay stated plainly in the UI | Lighter on privacy, cost and compliance at once |
| **No training on user data by default** | Say it in the privacy commitment in plain words | Do it once and the trust does not come back |
| **Secrets never hit disk** | Passwords, tokens and API keys are encrypted secret keys: never in environment variables, logs, diagnostic bundles or prompts; schema fields marked `secret` are masked automatically; record **where to get it**, never the value | Secret leaks almost always come out through logs and diagnostic bundles |
| **A licence allowlist** | MIT / Apache-2.0 / BSD / ISC / OFL are fine; MPL is fine if you do not modify its files; LGPL only dynamically linked; GPL / AGPL never linked into closed source (separate process only); no licence, no use; no forking, no vendoring | Licence problems get more expensive the later they surface |
| **External content is untrusted** | Web pages, mail, third-party responses and MCP responses are data, never instructions | Prompt injection comes in exactly here |
| **Decide what you will not do** | Write a "boundary" line: which categories are out | A product with no boundary gets dragged along by every request |
| **Check name collisions first** | System commands, companies in the field, trademarks, package names, domains — check them all; **repo / package namespace ≠ the public brand** | The cost of renaming grows exponentially with time |
| **An umbrella name plus suffixes** | A product line uses one umbrella name with suffixes (X / X Lite / X Cloud / X Console) rather than a new name per sub-product | Brand recognition concentrates; users see at a glance that it is one family |
| **An old project is an asset, not a starting point** | Take the conclusions, the designs and the traps (including "what was rejected and why"); do not copy whole blocks of code | Old code carries old constraints; the experience is what is actually valuable |
| **Design standards do not get downgraded for a minority** | The default look holds the design standard; accessibility is carried by a dedicated high-contrast look | Both are served, instead of both being compromised (a team may instead rule "the default must itself pass" — that is one ruling) |
| **Front end first** | No throwaway mockups: build the working feature front end plus a contract simulator, get the Requester's confirmation, then write the back end | He judges better when he can see it; the back end is then written once against a confirmed contract |
| **A living document** | Discussion is based on one summary that keeps being updated; original words are only appended; when a view changes, write "changed on <date> to …" | Discussion scattered through chat logs might as well not have happened |
